# コードレビュー基準

コードレビュー時に確認する観点をまとめる。現時点の基準として以下の項目を使用し、今後必要に応じて追記する。

## 1. アーキテクチャがルールに沿っているか

[アーキテクチャ設計](../design/アーキテクチャ.md)と、対象機能の詳細設計を実装と照合する。

- ファイルの配置と名前空間が、定めた層・業務の文脈に対応しているか。
- 各層の処理が、その層に定めた責務に収まっているか。
- クラス間の依存方向と、DB・外部サービスとの境界が設計に沿っているか。
- 更新と参照が目的に応じて分かれ、ドメインモデル・参照用DTO・永続化モデルがそれぞれの役割を担っているか。

### モデルの役割を実装から確認する

- ドメインモデルが、値の保持に加えて業務ルール・不変条件・状態遷移を守っているか。
- ORMによる保存・取得の機能を、ドメインの業務ルールと取り違えていないか。
- 参照用DTOが表示に必要な情報を表現し、ORMのモデルがそのまま境界の外へ返されていないか。参照データの取得にORMを使うことと、返却モデルの役割を区別する。
- 業務の振る舞いと保存形式が、必要な変換を通じて対応しているか。例えば業務上の状態を別の型で表し、DBでは`state`カラムに保存する構成では、保存・復元の両方向で意味と制約が保たれるか。
- 集約が守る整合性の範囲が明確で、関連するデータの更新がその範囲のルールを守っているか。

役割の分離は、目的ごとに必要な構造や制約に基づいて判断する。クラス数や同じ形のモデルの数を増やすこと自体を評価しない。

## 2. ファイル名・クラス名が実態と一致しているか

名前から読み取れる役割と、ファイルやクラスが実際に担当する処理を照合する。

- ファイル名が内容を表しているか。PHPのクラスファイルはクラス名と一致しているか。
- クラス名が扱う業務概念・利用目的・責務を表しているか。
- `Repository`、`QueryService`、`Handler`、`Result`などの名前が、実際の役割と一致しているか。
- 設計書や用語集で使っている言葉と、名前の意味が一致しているか。
- 利用者の目的を実行するユースケースが、その目的に対応したHandlerとして表現されているか。広い意味の`Service`名の下に異なる目的の処理が集まっていないか。

## 3. メソッド名と実際の処理が一致しているか

メソッド名を、引数・戻り値・処理内容・副作用と照合する。JavaScriptの関数も同じ観点で確認する。

- 名前が示す操作を実際に行っているか。
- 対象・条件・結果が、名前から想定できる内容と一致しているか。
- 取得・判定・変換を表すメソッドに、名前から予想できない保存・削除・外部送信などが含まれていないか。
- `is…`や`has…`は対応する真偽を、`get…`や`find…`は対象の取得を表しているか。
- `handle`など役割上共通のメソッド名は、所属クラス名と合わせて実行する目的が読み取れるか。

### 名前を見直す順序

1. 実際の処理と副作用を読む。
2. 一連の処理が実現する利用者の目的を確認する。
3. その目的を表す名前かを判断する。
4. 異なる目的が混在していれば、責務の分割も検討する。

例えば、`join`にプラン選択・見積もり・決済への遷移まで含まれる場合は、全体が「入会申し込み」という目的に対応するかを確認する。
対応する場合は、その目的を表す名前にする。個々の処理が同じ目的を達成するための手順なのか、独立した目的なのかを見極め、命名と責務の範囲を揃える。

## 4. テスト名・入力値・期待値が検証内容と一致しているか

PHPUnitのテストメソッド名は`test_日本語での説明`とする。

- 日本語の説明から、何をしたときに何が起きるか読み取れるか。
- 「正常系」「正しく動く」などの曖昧な表現を、具体的な操作・条件・期待結果で説明しているか。
- 説明に使う言葉が、利用者の操作や設計書の業務用語と一致しているか。
- テストの準備・実行・アサーションが、名前に書かれた条件と期待結果を実際に検証しているか。
- 名前が示す範囲を、アサーションで保証できているか。例えばHTTP 200の確認だけで、表示内容や保存結果まで検証したことにしていないか。

### 命名例

以下は命名方法の例。実際の機能に合わせて条件と結果を記述する。

| 曖昧な名前 | 具体的な名前 | 必要な検証 |
| --- | --- | --- |
| `test_正常系` | `test_トップページへのアクセスでHTTP200を返す` | GETリクエストに対してHTTP 200を返す |
| `test_保存できる` | `test_入力したタイトルで下書きを保存できる` | 入力したタイトルが下書きとして保存される |
| `test_入力チェック` | `test_タイトルが空の場合は入力エラーを返す` | タイトルを空にし、その項目の入力エラーが返る |
| `test_更新できる` | `test_タイトルを変更しても本文は変わらない` | タイトルが変更され、本文が元の値のままである |

### テストメソッド内で入力値と期待値を追えるか

Factoryやprivateメソッドによるデータ作成は利用してよい。検証に関係する値はテストメソッドで明示し、Factoryの属性やヘルパーの引数として渡す。

- どの値を準備し、どの値を処理に渡し、何を期待しているかをテストメソッドから読み取れるか。
- assert対象の値が、Factoryのランダム値やヘルパー内部の固定値に隠れていないか。
- データ作成用ヘルパーが、テストで指定した値をそのまま使っているか。
- アサーションをヘルパーにまとめる場合も、期待値をテスト側で指定して引数に渡しているか。
- 更新の検証では更新前後に異なる値を使い、更新されなかった場合に失敗するか。
- 期待値を実際の処理結果から作り直していないか。変換・計算の検証では、仕様から決めた期待値を置いているか。
- 検証に関係しない補助データはFactoryの既定値に任せ、検証の意図が読み取りやすいか。

以下は、記事のタイトル更新を想定した記述例。クラス・ルート・カラムは例示であり、実際の機能設計に合わせる。

```php
public function test_タイトルを変更しても本文は変わらない(): void
{
    $originalTitle = '変更前のタイトル';
    $updatedTitle = '変更後のタイトル';
    $body = '変更しない本文';
    $article = $this->createArticle($originalTitle, $body);

    $response = $this->patchJson('/articles/'.$article->id, [
        'title' => $updatedTitle,
    ]);

    $response->assertSuccessful();
    $this->assertDatabaseHas('articles', [
        'id' => $article->id,
        'title' => $updatedTitle,
        'body' => $body,
    ]);
}

private function createArticle(string $title, string $body): Article
{
    return Article::factory()->create([
        'title' => $title,
        'body' => $body,
    ]);
}
```

この例では、データ作成を共通化しつつ、変更前の値・送信する値・保存後に期待する値をテストメソッド内で確認できる。

## 5. 一連の処理で目的を達成できるか

コントローラーからユースケース、ドメイン、永続化・外部連携、レスポンス・画面表示まで、対象機能に必要な流れを追う。

- 設計書にある「誰が何を実現したいか」と、その達成条件を確認できるか。
- 入力から最終結果までをつなげると、利用者が目的を達成できるか。
- 個々のメソッドの成功に加えて、目的に必要な保存結果・取得結果・画面への反映まで成立しているか。
- 処理の途中で失敗した場合の状態や利用者への通知が、設計した振る舞いと一致しているか。
- 目的に対応する受入条件を、テストや動作確認で確かめられているか。

### 目的と変更箇所の対応を追えるか

- 目的・要件・受入条件から、担当するユースケース・ドメインのルール・テストをたどれるか。
- 達成条件が変わった際に、修正するコードと影響を確認するテストを特定できるか。
- 一つの目的の変更が別の目的へ影響する箇所では、その依存と理由を説明できるか。

### 事前条件・不変条件・事後条件がつながっているか

| 条件 | 確認する内容 | 注文数が1〜200というルールの例 |
| --- | --- | --- |
| 事前条件 | 呼び出し前の約束と、その検証箇所が明確か | 生成時に1〜200の入力を受け付け、範囲外の扱いが決まっている |
| 不変条件 | 生成・復元・変更の各経路で有効な状態を保つか | 保持する注文数が常に1〜200である |
| 事後条件 | 正常終了後の値や状態が仕様を満たすか | 加算後の値が計算結果と一致し、1〜200に収まる |

- 各条件が設計書に明記され、対応する実装とテストがあるか。
- 境界値・条件違反・状態変更後を検証し、呼び出し側の入力検証だけに不変条件の保証を任せていないか。
- 加算で上限を超えるなど正常終了できない場合は、エラーと変更前の状態の扱いが仕様・テスト・実装で一致しているか。

目的の達成担当が条件と実装の対応を確認し、テストコード担当が対応する入力値・期待値・アサーションを確認する。

## 6. テストを実行して結果を確認したか

コードレビューでは、対象コードの静的チェックとテストを実行する。

```sh
sh scripts/check.sh
docker compose run --rm -T app composer test
```

- 実行コマンド、対象、成功・失敗、失敗時の内容を記録する。
- 関連テストを個別実行した場合も、最後に全体のテストを実行して影響を確認する。
- 修正後は影響する検査とテストを再実行し、最新のコードに対する結果を確認する。
- 未実行・スキップされたテストは理由を記録し、検証済みの範囲と区別する。

## 7. コメント・PHPDocが読み手に必要な情報を伝えているか

[コーディング規約](../design/コーディング規約.md)の「コメントとPHPDoc」に沿って確認する。

- 人間の読み手が理解しやすい言葉を選び、曖昧な表現や説明のない略語を避けているか。
- 理由・前提・制約など、理解に必要な内容が十分に書かれているか。
- 同じ説明の繰り返しや、コードの逐語的な言い換えによって過度に長くなっていないか。
- その場所を読む際に必要な説明か。メソッドの呼び出し条件はPHPDoc、局所的な判断理由は該当処理の近く、全体の設計背景は設計書など、内容に合う場所に書かれているか。
- コメントの説明と実際の処理が一致しているか。
- `: array`に対する`@return array`のように、型宣言と同じ情報を繰り返すだけのPHPDocがないか。
- 配列のキー・要素・構造の型が具体的で、実際のデータと一致しているか。
- 引数の型や名前だけでは分からない単位・用途・制約などが、PHPDocで補足されているか。

## 8. カテゴリ別のサブエージェントによるレビュー

コードレビューは、以下のカテゴリごとに別のサブエージェントへ分担する。
各エージェントが担当範囲に集中できるよう、親エージェントが対象の差分と参照資料を整理する。

| カテゴリ | 担当する基準 |
| --- | --- |
| アーキテクチャ | 1. 配置・責務・依存関係・モデルの役割・集約 |
| ファイル・クラスの命名 | 2. 名前と実際の役割 |
| メソッドの命名 | 3. 名前と実際の処理 |
| テストコード | 4. 日本語の説明・入力値・期待値・検証内容の一致、5の条件に対応するテスト |
| 目的の達成 | 5. 処理全体・変更箇所・事前条件・不変条件・事後条件 |
| 検査・テスト実行 | 6. 実行結果の確認 |
| コメント・PHPDoc | 7. 分かりやすさ・過不足・記載場所・型と引数の補足 |

### 分担と結果の統合

1. 親エージェントがレビュー対象の差分・コードの状態を確定し、カテゴリごとに対象ファイル、必要な設計書、確認観点を渡す。
2. 各サブエージェントは担当カテゴリを確認する。呼び出し先や呼び出し元など、判断に必要な関連コードも読む。
3. 同時実行数の上限に合わせてカテゴリを順番に割り当てる。カテゴリごとに独立したコンテキストを使い、会話全体の複製を避ける。
4. 検査・テスト実行はその担当に集約し、同じ実行環境やテスト用DBを複数エージェントが同時に変更することを防ぐ。
5. 各担当は、確認した範囲、指摘（ファイル・行・根拠・影響）、指摘なしの項目、未確認事項を親へ報告する。レビュー中のコード修正は親が調整する。
6. 親エージェントが全カテゴリの報告を照合し、重複・矛盾を整理する。未確認のカテゴリを残したままレビュー完了としない。

目的達成の担当には処理の入口から結果までの流れを渡し、ファイル単位の分担による確認漏れを防ぐ。
サブエージェントを使用できない場合はその制約を報告し、分担による確認が未実施であることを明記する。
