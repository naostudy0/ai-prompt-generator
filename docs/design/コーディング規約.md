# コーディング規約と静的チェック

[開発方針](../spec/開発方針.md)と[アーキテクチャ設計](アーキテクチャ.md)に加えて、本書を実装時に適用する。

## 採用基準

| 対象 | 基準 | 自動検査 |
| --- | --- | --- |
| PHP | PSR-1 / PSR-12、既存のPSR-4オートロード | Laravel Pintの`psr12`プリセット |
| PHPの型・呼び出し | 明示的な型、Laravelの型解決 | PHPStan＋Larastan、level 8 |
| JavaScript | ESLint公式recommended＋本書の追加ルール | ESLint、警告も失敗として扱う |
| JS・CSSの整形 | Prettier設定に統一 | Prettierのcheck |
| Blade・HTML | 以下のテンプレート規約 | レビューと必要な画面・HTTPテスト |

JavaScriptはESLint公式推奨設定を基準にする。
ESLintは不具合につながる記述を検出し、Prettierは見た目を整える。それぞれの役割を分ける。

## 共通

- UTF-8、LF、スペースでインデントし、末尾に改行を入れる。PHP・JS・CSSは4スペース。
- クラスはPascalCase、メソッド・変数はcamelCase。PHPUnitのテストメソッドは下記のテスト命名規約に従う。業務用語と配置はアーキテクチャ設計に合わせる。
- 一つの処理に異なる利用目的を混ぜない。コメントは処理の言い換えより、制約の理由や判断を説明する。
- 不要なコメントアウト・デバッグコード・未使用コードを残さない。
- 外部入力と外部サービスの応答は境界で検証する。例外を握り潰さず、責務に応じて変換・報告する。

## PHP

- 書式は`pint.json`を正とし、Pintで整形する。PSRで定義されない新しい構文もツールの対応範囲で統一する。
- 引数・戻り値・プロパティには可能な限りネイティブ型を付ける。配列要素やジェネリクスなどはPHPDocで補う。
- 不変の値・DTOではreadonlyを活用し、公開プロパティの変更によって不変条件を迂回させない。
- 型が分からないことを理由に`mixed`や無根拠な`@var`で解析を回避しない。外部入力は検証して型を絞る。
- PSR-12はコーディングスタイルであり、DDDの責務や依存方向は別途設計書とレビューで確認する。

## コメントとPHPDoc

- 読み手が理解しやすい具体的な言葉を使い、業務用語は設計書と揃える。
- 理解に必要な理由・前提・制約を簡潔に書く。短さだけを優先して必要な説明を省かず、同じ説明の繰り返しを避ける。
- コメントは、その場所の処理や呼び出し方を理解するために必要な情報を書く。全体の設計背景などは対応する設計書にまとめ、必要に応じて参照する。
- 型宣言や名前から十分に読み取れる内容をPHPDocで繰り返さない。例えば戻り値が`: array`の場合、追加情報のない`@return array`は書かない。
- 配列にはキーと要素の型を記述する。例：`array<int, string>`。連続した添字の一覧には`list<string>`、決まったキーを持つ構造には`array{title: string, body: string}`など、実態に合う型を使う。引数・戻り値・プロパティとも同じ方針とする。
- 型や引数名だけでは意味が分からない場合は、PHPDocに単位・用途・許容範囲・特殊な値の意味など、呼び出しに必要な情報を補う。説明が必要なら、ネイティブ型と同じ型を`@param`に記載してよい。
- コメント・PHPDocの説明と型は、実際の処理や値に合わせて更新する。

### PHPDocの例

以下は宣言の記述例。実際の機能で扱う型と条件に合わせる。

```php
/**
 * @return array<int, string> 記事IDをキー、タイトルを値とする対応表
 */
public function getArticleTitles(): array;

/**
 * @param int $timeout 外部サービスの応答を待つ秒数。1以上を指定する。
 */
public function request(int $timeout): string;
```

最初の例は`: array`だけでは分からないキー・要素の型と意味を補っている。
次の例は`int`だけでは分からない単位と範囲を補っている。戻り値の意味が十分に明確な場合、`@return string`を重複して記載する必要はない。

## テストの命名と検証値

PHPUnitのテストメソッドは`test_日本語での説明`の形にする。
操作・条件・期待結果が読み取れる言葉を選び、説明と実際のアサーションを一致させる。
例：`test_トップページへのアクセスでHTTP200を返す`。
データ作成にはFactoryやprivateメソッドを利用できる。検証に関係する入力値・期待値はテストメソッドに明示し、データ作成やアサーションのヘルパーには引数で渡す。
詳しい例と確認観点は[コードレビュー基準](../review/コードレビュー基準.md)を参照する。

## JavaScript

- ES Modulesを使う。原則`const`、再代入が必要な場合だけ`let`とし、`var`は使わない。
- 比較は`===` / `!==`を使い、条件分岐・ループには波括弧を付ける。
- 非同期処理は`async` / `await`を基本とし、`fetch`のHTTPエラーと通信エラーの両方を処理する。
- ブラウザー向けコードとNode.js用設定を分ける。ブラウザーコードでNode.jsのグローバルを使わない。
- 未使用変数・未定義変数・`console`・`debugger`を残さない。障害表示は画面上で利用者に伝える。
- セミコロンあり、シングルクォート、末尾カンマあり。詳細はPrettier設定に従う。
- JavaScriptは`resources/js/`に置く。Blade内のインラインスクリプトへ業務処理を記述しない。

## Blade・HTML・CSS

- Bladeは表示の責務に限定し、DBアクセスや業務判断を記述しない。
- 文字列はBladeのエスケープ出力、動的なDOM更新は`textContent`を基本にする。生HTMLの出力には根拠と安全な処理が必要。
- セマンティックなHTMLを使用し、入力にはlabel、操作にはbuttonを使用する。キーボード操作とエラー表示を確認する。
- CSSは`resources/css/`に置く。Tailwindを使う場合も表示ロジックと業務ロジックを混在させない。
- PintはBladeを対象にせず、現在のESLint・Prettier設定もBladeを解析しない。Blade構文・画面の正しさは関連するHTTPテスト・ブラウザー確認で補う。CSSは整形のみで、意味的なlintは未導入。

## 実行方法

PHP・Composer・Node.js・npmはDocker内で実行する。初回は依存をインストールする。

```sh
docker compose build app
docker compose run --rm app composer install
docker compose run --rm node npm ci
```

開発後の必須チェック（ファイルを変更しない検査）：

```sh
sh scripts/check.sh
```

内部では以下を順に実行し、どれかが失敗したら終了する。

```sh
docker compose run --rm -T app composer check
docker compose run --rm -T node npm run check
```

整形の修正：

```sh
docker compose run --rm app composer format
docker compose run --rm node npm run format
docker compose run --rm node npm run lint:fix
```

修正後は差分を確認し、必須チェックを再実行する。自動修正で解決できない指摘はコードを修正する。
PHPStanの対象は`app/`・`bootstrap/app.php`・`bootstrap/providers.php`・`config/`・`database/`・`routes/`・`tests/`。
PintはプロジェクトのPHP、ESLintは生成物を除くJS、Prettierは同じJSと`resources/css/`のCSSを対象とする。
依存・生成物・キャッシュは対象外。検査対象の追加は設定と本書を合わせて更新する。

## 完了条件

コード・設定・依存の変更後は、変更言語にかかわらず`sh scripts/check.sh`を必ず成功させてから開発完了とする。
静的チェックはテストの代わりではない。振る舞いを変更した場合は関連テストも実行する。
文書だけの変更は文書リンクと整合性の確認でよい。
実行できなかった検査は理由とともに報告し、成功したことにしない。

解析レベルを下げる、対象を除外する、baselineや広範囲のignoreを追加することでエラーを消さない。
誤検知を抑制する必要がある場合は、理由・対象・最小範囲を明記し、設定変更をレビュー対象にする。
依存バージョンは`composer.lock`と`package-lock.json`で再現する。
