# F22 AI生成タググループの保存

関連文書：[機能概要](../../spec/機能概要.md)、[用語集](../../spec/用語集.md)、[アーキテクチャ](../アーキテクチャ.md)、[画面設計](../画面設計.md)、[F08 オプション項目の登録と選択](F08-オプション項目の登録と選択.md)、[F20 AIプロンプト生成](F20-AIプロンプト生成.md)

## 目的と背景

AIが生成した一枚分のプロンプトには、「黒髪ロングの女の子」「夕暮れの教室」「窓の外を眺めている」のように、別の生成でも再利用できる意味上のまとまりが含まれる。利用者がこれを日本語名と複数の英語タグの組として選んで保存し、既存のオプション項目と同じ操作で次回以降のプロンプトへ加えられるようにする。

候補はAIが提案するが、自動保存はしない。利用者の選択を最終判断とし、既存のオプション管理、出力順、コピー、人物LoRA差し替え等へ自然に連携させる。

## 要件とスコープ

| ID | 要件 |
| --- | --- |
| F22-R01 | F20の生成と同じ外部LLM応答で、日本語ラベルと複数の英語タグから成る再利用候補を1〜10件取得できる |
| F22-R02 | F20の出力形式が`natural_language`でも、再利用候補のタグは常にカンマ区切りのDanbooruタグ形式とする |
| F22-R03 | 候補は初期未選択とし、利用者が選択した候補だけを明示操作で保存する |
| F22-R04 | 保存先は未分類かつ複数選択のシステム管理グループ「AIプロンプト」とする |
| F22-R05 | 内部識別子でシステム管理グループを特定し、利用者が作成した同名グループと共存できる |
| F22-R06 | タグ集合を正規化して既存項目と重複判定し、重複は保存せず件数を通知する |
| F22-R07 | 生成失敗では既存出力を変更せず、保存失敗では生成済みプレビューと候補の選択状態を保つ |
| F22-R08 | 保存成功後はページ再読み込みなしでオプション一覧を再取得し、保存した候補を既存画面で利用できる |
| F22-R09 | システム管理グループ自体の名前・分類・順序・選択方式の変更と削除を禁止し、所属項目の編集・移動・並べ替え・削除は許可する |
| F22-R10 | 日本語ラベル、タグ内容、生成指示、LLMの生応答を通常ログへ記録しない |

対象は、F20の応答拡張、候補選択UI、選択候補の一括保存API、システム管理グループの識別と保護、保存後の既存オプション一覧更新である。

候補の再生成、候補内容の保存前編集、AIによるカテゴリ分類、生成履歴、複数シーンへの分割、候補の自動保存は対象外とする。

## 用語

- **再利用候補**：一つの日本語ラベルと、意味上のまとまりを表す複数の英語タグの組。
- **AIプロンプトグループ**：内部識別子`ai_prompt_suggestions`を持つシステム管理のオプショングループ。表示名は「AIプロンプト」。
- **正規化タグ集合キー**：カンマで分割したタグを正規化し、順序に依存しない重複判定へ用いる値。

## ユースケース1：再利用候補を含むプロンプトを生成する

- **入力**：F20と同じイラスト説明とプロンプト形式。
- **正常な流れ**：F20の一回の外部LLM呼び出しでpositive、negative、再利用候補を生成する。画面は各候補の日本語ラベルと英語タグをチェックボックス付きで表示する。
- **初期状態**：候補はすべて未選択とする。
- **事後条件**：候補を表示しただけではDBと既存出力を変更しない。「出力へ反映」と候補保存は独立した操作とする。
- **例外**：候補配列の欠落、0件、11件以上、項目の型・文字数・タグ内容の不正は、positive／negativeが妥当でも生成応答全体を不正として扱う。部分成功にはしない。

## ユースケース2：選択した候補を保存する

- **入力**：生成結果から利用者が選択した1〜10件の候補。
- **正常な流れ**：Applicationがトランザクション内でAIプロンプトグループを取得し、存在しなければ作成する。各候補を入力順に重複判定し、新規候補をグループ末尾へ保存する。
- **出力**：グループID、新規保存件数、重複件数を返す。全件が重複でも正常終了する。
- **画面更新**：新規保存または重複と判定された候補のチェックを外し、既存オプション一覧を再取得する。新規項目を自動選択はしない。
- **例外**：入力不正または保存失敗では一件も保存しない。生成済みpositive／negative、候補一覧、チェック状態を維持して再試行できるようにする。

## 業務ルール

### 候補の形式

- 一回の生成結果に1件以上10件以下を必須とする。
- `label`は前後空白を除いて1文字以上100文字以下とする。
- `tags`は文字列とし、カンマと空白を除いた文字を1文字以上含むことを必須とする。
- ラベルは利用者が元の説明との対応を判断できる自然な日本語とする。
- タグは候補単位で再利用可能なDanbooru形式の英語タグ群とし、カンマ区切りで返す。F20本体が自然文形式でもこの規則は変えない。
- 入力の主要な意味のまとまりを抽出し、過度に細かい一タグ単位や、説明と無関係な品質タグだけの候補を避けるようSystem Promptで指示する。
- AI提案の完全性やDanbooru上の厳密な存在を保証しない。保存前の利用者選択を品質管理の境界とする。

### 重複判定

正規化タグ集合キーは次の手順で作る。

1. `tags`をカンマで分割する。
2. 各要素の前後空白を除去し、空要素を除く。
3. 大文字・小文字を区別しない形へ変換する。
4. タグを並べ替え、順序に依存しないキーを作る。

AIプロンプトグループに現在所属する項目とキーが同じ候補は、日本語ラベルが異なっても重複とする。保存要求内で候補同士が重複する場合は最初の一件だけを保存対象とし、後続を重複件数へ加える。保存する`content`は正規化キーではなく、既存のプロンプト整形規則を通した提案順のタグ文字列とする。

AIプロンプトグループから別グループへ移動した項目は重複判定の対象外となり、同じタグ集合を再び保存できる。

### システム管理グループ

AIプロンプトグループは最初の候補保存時にだけ作成し、マイグレーション時には作成しない。固定値は次のとおり。

| 項目 | 値 |
| --- | --- |
| 内部識別子 | `ai_prompt_suggestions` |
| 表示名 | `AIプロンプト` |
| カテゴリ | 未分類（`null`） |
| 選択方式 | 複数選択 |

利用者作成グループには内部識別子を設定しないため、同名の「AIプロンプト」が存在しても別グループとして扱う。システム管理グループは、名前変更、カテゴリ変更、グループ順変更、選択方式変更、削除を拒否する。最後の項目を削除してもグループ自体は残す。

所属項目は通常項目と同様に、名前・内容の編集、グループ内並べ替え、別グループへの移動、削除を許可する。

## ドメインとApplication設計

F20の生成結果へ、ラベルとタグを持つ不変な再利用候補値の一覧を追加する。外部LLMアダプターは上流のsnake_caseをApplicationの値へ変換し、上限を含む応答検証を行う。

保存は複数の項目作成とグループの遅延作成を一つの整合性境界で扱うため、`Application/PromptPreparation/Writes`配下に専用の一括保存ハンドラーを置く。HTTPコントローラーへ重複判定やトランザクション制御を置かない。

`OptionPromptGroup`には、通常グループでは`null`、システム管理グループでは内部識別子を持つ属性を追加する。システム管理時の変更禁止は画面のボタン非表示だけにせず、更新・削除ユースケースからも拒否する。

Repositoryには内部識別子によるグループ取得を追加する。ハンドラーはDBトランザクション内で取得または作成、既存項目の参照、重複判定、新規項目の末尾追加を行う。

## 外部LLM応答

F20の構造化出力JSON SchemaとSystem Promptを次の形へ拡張する。

```json
{
  "positive_prompt": "1girl, solo, long black hair, looking outside, classroom, sunset",
  "negative_prompt": "low quality, blurry, bad anatomy",
  "reusable_tag_groups": [
    {
      "label": "黒髪ロングの女の子",
      "tags": "1girl, solo, long black hair"
    },
    {
      "label": "夕暮れの教室",
      "tags": "classroom, sunset"
    },
    {
      "label": "窓の外を眺めている",
      "tags": "looking outside, standing by window"
    }
  ]
}
```

追加取得のための二回目のLLM APIは呼ばない。応答トークンは増えるが、通信とモデル推論を重ねずに待ち時間を抑え、生成内容と候補の整合性も保つ。

## HTTP API

### 生成APIの拡張

既存の`POST /illustration-prompts/generate`成功レスポンスへ`reusableTagGroups`を追加する。

```json
{
  "positivePrompt": "1girl, solo, long black hair, looking outside, classroom, sunset",
  "negativePrompt": "low quality, blurry, bad anatomy",
  "model": "configured-model",
  "promptStyle": "danbooru_tags",
  "generationTimeMs": 3500,
  "reusableTagGroups": [
    {
      "label": "夕暮れの教室",
      "tags": "classroom, sunset"
    }
  ]
}
```

### 候補保存API

```http
POST /illustration-prompt-tag-groups
Accept: application/json
Content-Type: application/json
X-CSRF-TOKEN: <token>
```

リクエスト例：

```json
{
  "groups": [
    {
      "label": "夕暮れの教室",
      "tags": "classroom, sunset"
    }
  ]
}
```

成功レスポンスは、新規件数が0件の場合を含めて`200 OK`とする。このエンドポイントは単一リソースの作成ではなく、複数候補の保存判定を行うコマンドだからである。

```json
{
  "groupId": 12,
  "savedCount": 1,
  "duplicateCount": 0
}
```

入力は`groups`を必須配列かつ1〜10件とし、各項目へ生成応答と同じラベル・タグ検証を適用する。

| 失敗 | ステータス | 扱い |
| --- | --- | --- |
| 件数、ラベル、タグの入力不正 | 422 | 項目ごとの修正理由を返す |
| 保存中の予期しない障害 | 500 | 内部情報を含めず保存失敗を返し、トランザクションをロールバックする |

## 永続化

`option_prompt_groups`へnullableかつ一意な`system_key`列を追加する。既存行はすべて`null`とし、データ移行でAIプロンプトグループを作らない。複数の`null`を許容するDB制約を使用する。

候補は既存の`option_prompts`へ、`name = label`、`content = tags`として保存する。専用候補テーブルは設けず、保存後の選択・編集・出力合成はF08の仕組みを再利用する。

## 画面とフロントエンド

F20の生成結果モーダルに、positive／negativeプレビューとは別に「再利用できるタグ候補」を表示する。各行は未選択のチェックボックス、日本語ラベル、英語タグを持つ。

一件以上を選択すると「選択した候補を保存」を実行できる。保存中は二重送信を無効化する。保存成功時は保存件数と重複件数を通知し、処理対象のチェックを外してオプション一覧を再取得する。保存した項目へ自動的にチェックは入れない。

保存失敗時はpositive／negativeプレビュー、候補、チェック状態を変えず、再試行可能なメッセージを表示する。「出力へ反映」の成否と候補保存の成否は互いに依存させない。

オプション管理画面ではAIプロンプトグループがシステム管理であることを示し、グループ自体の変更・移動・削除操作を表示または有効化しない。項目単位の編集・移動・並べ替え・削除操作は通常どおり表示する。

## プライバシーとログ

生成APIと保存APIのログには、追跡ID、結果分類、件数、処理時間等の運用情報だけを記録できる。イラスト説明、日本語ラベル、タグ、positive／negative、System Prompt、LLMの生応答は記録しない。例外メッセージに上流本文が含まれる場合もそのままログへ渡さない。

## テスト方針

実際の外部LLMと実データは使用しない。LLMポートのFake、Laravel HTTPクライアントのFake、テストDB、factory、JavaScript DOMテストだけを使う。

主な検証範囲は次のとおり。

- 両プロンプト形式で候補がDanbooruタグ形式として要求・返却される。
- 候補1件・10件の成功、0件・11件・配列欠落・不正型・ラベル長・空タグの失敗。
- 候補不正時にpositive／negativeだけを成功扱いしない。
- 候補の初期未選択、選択候補だけの送信、二重送信防止。
- 最初の保存時だけシステム管理グループを作り、利用者作成の同名グループと共存する。
- 空白、大文字・小文字、タグ順の違いを重複として扱う。
- 保存要求内の重複は最初だけ保存し、後続を重複件数へ加える。
- グループ外へ移動済みの項目は重複判定対象にしない。
- 一部処理失敗時にグループ作成を含む全変更をロールバックする。
- システム管理グループの変更・並べ替え・削除をHTTP経由でも拒否する。
- 所属項目の編集・移動・並べ替え・削除を許可し、空になってもグループを残す。
- 保存成功後の一覧再取得、チェック解除、非自動選択。
- 保存失敗時にプレビューとチェック状態を維持する。
- ログへ入力・候補・生成結果・上流本文を含めない。

## 受け入れ条件

- 例示の説明から、positive／negativeと、日本語ラベル・複数タグの候補が一回の生成操作で表示される。
- 利用者が選択した候補だけが「AIプロンプト」グループへ保存され、ページ再読み込みなしで既存オプションとして選択できる。
- 利用者作成の同名グループがあっても、保存先と管理制約を取り違えない。
- 同じタグ集合は表記上の空白、大文字・小文字、順序が違っても重複保存されず、結果件数が通知される。
- 候補を保存しても現在のオプション選択や生成済み出力を勝手に変更しない。
- 保存や生成に失敗しても部分保存や既存出力の破壊がなく、再試行できる。

## 設計判断

- 候補は同じLLM応答へ含め、追加API呼び出しによる待ち時間を避ける。
- 保存済み候補は専用データ構造ではなく既存オプションとして扱い、出力・編集・並べ替えの仕組みを再利用する。
- 表示名ではなくnullableな内部識別子でシステム用途を表し、利用者の命名を制限しない。
- 重複は日本語名ではなくタグ集合の意味上の一致で判定する。
- AIの提案を自動採用せず、利用者がチェックした候補だけを保存する。

現時点で実装を妨げる未決事項はない。
