# F25 整合性のあるランダムイラスト案

- 関連：[機能概要](../../spec/機能概要.md)、[用語集](../../spec/用語集.md)、[アーキテクチャ](../アーキテクチャ.md)、[画面設計](../画面設計.md)、[F08](F08-オプション項目の登録と選択.md)、[F15](F15-選択画面の整理と管理操作の分離.md)、[F20](F20-AIプロンプト生成.md)、[F22](F22-AI生成タググループの保存.md)

## 目的と背景

利用者が具体的なイラスト案を思いついていないとき、登録済み候補の偶然性を活かしながら、意味の通る一枚分の案を得られるようにする。

各オプションを独立に無作為抽出すると、「走りながら椅子に座る」のように、個々のタグは有効でも組み合わせとして矛盾する。そこで、場所だけを通常の乱数で発想の起点として選び、手動選択済みの条件とともに外部LLMへ渡す。LLMはまず日本語の完成イメージを提案し、利用者が編集・確認した後に、既存項目の選択と不足分の一時候補へ変換する。

この機能の価値は厳密なランダム性ではなく、利用者が普段選ばない組み合わせに出会いながら、破綻した組み合わせを手で直す負担を減らすことにある。

## アプローチ

| 方式 | 利点 | 課題・判断 |
| --- | --- | --- |
| 二段階AI方式 | 日本語案を自由に編集してから既存項目とタグへ変換でき、確認対象が分かりやすい | 外部LLMを最大二回呼ぶ。今回採用する |
| 一括AI方式 | 編集しなければ一回の呼び出しで完了する | プレビューで破棄する選択結果まで先に作り、編集後は再解析が必要になる |
| 互換ルール併用方式 | 応答が決定的で外部LLMの費用を抑えられる | 項目間の互換関係を利用者が登録・保守する必要があり、今回の目的に合わない |

## 要件とスコープ

| ID | 要件 |
| --- | --- |
| F25-R01 | オプションブロックを複数個、場所候補の抽選元として指定できる |
| F25-R02 | 手動選択済み項目を固定条件とし、場所が未選択なら登録済み場所候補から一件を通常の乱数で選べる |
| F25-R03 | 場所候補が存在しなくても、LLMに場所を含むイラスト案を補わせて生成を継続できる |
| F25-R04 | 固定条件と起点の場所に矛盾しない、日本語の一枚分のイラスト説明をプレビューできる |
| F25-R05 | プレビューの日本語説明を編集でき、別案では固定条件以外を破棄して場所から引き直せる |
| F25-R06 | 編集後の説明を反映すると、登録済み項目はIDで選択し、不足要素は今回限りの一時候補としてpositiveまたはnegativeへ加え、現在の両出力を新しい結果で置き換えられる |
| F25-R07 | 固定条件と編集内容が矛盾する場合は固定条件を優先し、修正内容を利用者へ示せる |
| F25-R08 | positiveの一時候補を使用後に選んで、通常のオプション項目として保存できる。negativeの一時候補は初回範囲では保存しない |
| F25-R09 | 人物LoRAは未選択を許容し、ランダム生成によって自動選択しない。選択済みの場合だけ固定条件として扱う |
| F25-R10 | プレビューまたは反映に失敗しても現在の選択、表示済み出力、編集した説明を失わない |

初回範囲は一枚分の案、場所候補の役割設定、日本語案の生成・編集・再提案、編集後の解析、既存項目の選択、一時候補の反映と保存である。

複数案の同時比較、生成履歴、重み付き抽選、同じ場所を維持した再提案、人物LoRAの自動選択、画像生成結果を使った自動評価、項目間の互換ルール登録は対象外とする。

## 用語と状態

- **場所候補ブロック**：ランダム生成の起点となる項目を提供するオプションブロック。表示名とは別の役割で識別する。
- **固定条件**：ランダム生成を開始した時点で利用者が手動選択していたデフォルトpositive／negative、人物LoRA、トリガー、服装、衣装LoRA、オプション項目など。LLMが削除・置換してはならない。
- **起点場所**：登録済み場所候補から乱数で選んだ一件。日本語案を作る制約だが、利用者が説明内の場所を書き換えた場合は固定条件として扱わない。
- **ランダムイラスト案**：固定条件と起点場所からLLMが提案する、編集可能な日本語の一枚分の説明。
- **一時候補**：編集後の説明に必要だが登録済み項目では表現できないため、LLMが日本語ラベル、positiveまたはnegative、英語タグ群として補った今回限りの要素。

画面では次の状態を区別する。

1. 元の選択状態と表示済み出力。
2. 生成開始時に取得した固定条件。
3. 抽選した起点場所。
4. 編集中の日本語案。
5. 反映解析で得た既存項目の選択案と一時候補。

プレビューを閉じる、別案を作る、または外部LLM呼び出しに失敗しても、明示的な反映前に元の選択状態と表示済み出力を変更しない。

## 場所候補の管理

`OptionPromptGroup`へ、ランダム生成上の役割を表す任意属性を追加する。初回に定義する役割は`location_source`だけとし、通常のブロックは役割なしとする。表示名、カテゴリ、選択方式、表示順とは独立させる。同名ブロックや改名後のブロックもIDと役割で正しく識別する。

複数ブロックへ`location_source`を設定できる。管理画面で役割を設定・解除し、通常画面では場所候補であることを補助表示する。場所候補ブロック内の項目は、ブロックの選択方式にかかわらず、起点抽選では一件ずつ同じ重みの候補として扱う。空のブロックは抽選対象に含めない。

選択済みの場所候補が一件ある場合は抽選せず、その項目を起点場所と固定条件の両方として扱う。複数選択されている場合はすべてを固定条件としてLLMへ渡し、起点を一件に絞らない。選択済み場所がなく候補がある場合だけ、暗号学的な予測不能性を品質要件としない通常の乱数で一件を選ぶ。ただし、テストで抽選結果を固定できる境界を設ける。

場所候補ブロックまたはその項目が一件もない場合、起点場所を空としてLLMへ渡し、説明に適切な場所を補うよう依頼する。この場所は一時候補になり得る。

## ユースケース1：日本語のランダムイラスト案を作る

### 入力

- 生成開始時の固定条件。表示名とプロンプト文面を含むが、秘密情報や不要な管理情報は含めない。
- 選択済み場所、またはサーバーが抽選した起点場所。

### 正常な流れ

1. 画面は現在の選択を固定条件として送信する。
2. サーバーは送信されたIDを現在の登録内容と照合し、表示名や文面をクライアント入力だけから信用しない。
3. 選択済み場所がなく場所候補が存在する場合、抽選境界を通じて一件を選ぶ。
4. Applicationは固定条件と起点場所を外部LLMポートへ渡す。
5. LLMは矛盾のない日本語説明を一件返す。人物LoRAが未選択なら、特定の登録済み人物LoRAを勝手に選ばない。
6. 画面は固定条件、起点場所、編集可能な日本語説明をプレビューする。

### 別案

「別案を作る」は現在の未反映案を破棄し、生成開始時の固定条件を維持したままユースケースを最初から実行する。選択済み場所が固定条件でなければ場所も再抽選する。同じ場所のまま内容だけを再生成する操作は初回範囲に含めない。

### 出力

- 画面内で古い応答を識別する案ID。
- 日本語説明。
- 固定条件の表示用概要。
- 起点場所の表示用概要。起点がない場合は`null`。
- 使用モデルと生成時間。

案IDは画面が反映中の応答を現在のプレビューと照合するために使用し、生成履歴として永続保存しない。同じタブ内のプレビュー状態として保持する。

## ユースケース2：編集した案を既存選択と一時候補へ変換する

### 入力

- 画面が管理する案ID。
- 編集後の日本語説明。
- 生成開始時の固定条件ID集合。

### 正常な流れ

1. サーバーは固定条件の現在の登録内容と、選択可能な既存オプション項目を取得する。
2. LLMへ編集後の説明、固定条件、既存項目のID・登録名・文面・所属ブロックを渡す。
3. LLMは、既存項目から選ぶID、positive側とnegative側の一時候補、固定条件と説明の矛盾調整結果を構造化して返す。
4. サーバーは返されたIDが候補集合に存在すること、`single`ブロックの上限、固定条件の保持、一時候補の形式と件数を検証する。
5. 固定条件と編集内容が矛盾する場合、固定条件を残し、説明または補完内容を固定条件に沿う形へ調整する。成功結果に調整後の日本語説明と理由を含める。
6. 画面は固定条件を維持したまま既存項目の選択を反映し、一時候補を識別可能なセクションとして新しいpositive／negativeを組み立て、現在の両出力を置き換える。

起点場所は編集後の説明より優先しない。たとえば起点が「教室」でも説明が「図書館」へ編集されていれば、教室を強制選択せず、図書館を既存項目または一時候補として反映する。

固定条件以外の生成前選択は存在しないため、AI選択は各ブロックの現在の選択へ追加する。`single`ブロックに固定条件がある場合、AIは別項目を選べない。固定条件のない`single`ブロックでは最大一件、`multiple`では複数件を選べる。

### 一時候補

一時候補は0件以上10件以下とし、各候補に次を持たせる。既存項目だけで説明を表現できる場合は0件を正常とする。

- 日本語ラベル。
- 適用先の`positive`または`negative`。
- カンマ区切りの英語タグ。

一時候補はDBへ自動保存しない。出力へ反映した後も由来を保持し、通常の手編集、コピー、人物LoRA差し替え、クリップ保存を妨げない。出力欄を直接編集した内容を一時候補へ逆同期しない。

## 一時候補の保存

利用者は反映済みのpositive一時候補から必要なものだけを選び、登録名と保存先オプションブロックを指定して保存できる。保存しない候補は次の案の反映またはページ終了時に破棄する。negative一時候補は初回範囲では今回の出力だけに使用し、保存操作を提供しない。

保存にはF08の通常オプション項目作成を再利用する。F22のシステム管理「AIプロンプト」グループへ自動保存しない。利用者が保存先を決めることで、その後の分類・出力順・選択方式を既存の管理方法と揃える。negative候補の保存は、F16の連動negativeが実装された後に別途拡張する。

## 外部LLMの指示と検証

日本語案生成では次をSystem Promptで要求する。

- 固定条件を変更、省略、別人物へ帰属させない。
- 同時に成立しない姿勢や動作を組み合わせない。
- 人物が指定されていなければ、人物の存在を必須にしない。
- 起点場所があれば、その場所で自然に成立する動作、構図、表情、照明を提案する。
- タグ列挙ではなく、利用者が完成イメージを判断できる簡潔な日本語説明を返す。

構造化応答の形式逸脱を抑えるため、生成時のtemperatureは0とする。発想の偶然性は、場所の通常乱数による抽選と利用者が固定した条件の組み合わせで確保し、JSON構造自体の揺らぎには依存しない。

反映解析では、自由なプロンプト全文ではなく、既存項目ID、調整後の日本語説明、調整理由、不足分だけを構造化出力させる。外部応答はJSON Schemaとアプリケーション側検証の両方を通す。存在しないID、固定条件の欠落、`single`違反、空のラベル・タグ、件数超過、未知の適用先を含む応答は反映しない。

登録済み項目がモデルのコンテキスト予算を超える場合に、末尾を黙って切り捨てない。使用モデルの入力上限、固定条件と説明に必要な予約量、項目一件ごとの直列化後サイズから全件送信可能か事前判定する。超える場合はLLMを呼ばず、候補を絞る必要があることを案内する。意味検索などによる自動絞り込みは、品質評価と方式を別途設計してから導入する。

LLMが意味上の矛盾を必ず発見することや、美的に優れた案を返すことは決定的に保証できない。プログラムが保証するのは、固定条件の保持、構造、候補ID、選択数、失敗時の非反映である。品質は固定した架空の条件集合を人が評価する。

## Applicationと境界

日本語案の生成と反映解析はいずれも外部副作用を伴うため`Application/PromptPreparation/Writes`へ置き、HTTPでは`POST`を使う。DBは更新しないが、外部LLMの費用と副作用を伴うためQueriesには分類しない。

- `GenerateRandomIllustrationIdea`：固定条件の検証、場所抽選、案生成を調整する。
- `ResolveRandomIllustrationIdea`：編集後説明、固定条件、既存候補をLLMへ渡し、構造化結果を検証する。
- `RandomSource`：場所抽選を本番実装とテスト用Fakeに分けるApplicationポート。
- `RandomIllustrationIdeaGenerator`：日本語案生成の外部LLMポート。
- `RandomIllustrationIdeaResolver`：既存項目選択と一時候補生成の外部LLMポート。

既存F20と同じ外部LLM接続設定、タイムアウト、エラー変換、ログ方針を再利用できる。ただし、F20の自由入力から直接positive／negativeを作るユースケースへ統合せず、入出力と目的を分ける。

## HTTP API

| 目的 | メソッド・URL | 主な入力・結果 |
| --- | --- | --- |
| 日本語案を生成 | `POST /random-illustration-ideas` | `fixedSelections`を受け、案ID、日本語説明、固定条件概要、起点場所、モデル、時間を返す |
| 編集後の案を解析 | `POST /random-illustration-ideas/resolve` | `ideaId`、`description`と固定条件IDを受け、同じ`ideaId`、調整後説明、既存項目ID、一時候補、調整内容を返す |

入力不正は422、外部LLMの接続失敗・タイムアウトは503、応答形式不正は502とする。外部LLM処理を自動再送しない。利用者の明示操作で再試行する。

案IDに対応する本文をDBへ保存しないため、反映APIではクライアントが編集後説明と固定条件IDを再送する。案IDはクライアントが同じプレビューに対する重複操作や古い応答の表示を防ぐ相関IDであり、サーバーが現在の案との一致や過去本文を検証・復元できることを意味しない。

## 画面

通常の選択画面に「ランダム案を作る」入口を置く。生成中は二重送信を防ぎ、既存の選択と出力を変更せず保持する。プレビューモーダル表示中は背面を操作できない。固定条件を変える場合はプレビューを閉じて通常画面へ戻る。

プレビューには次を表示する。

1. 変更されない固定条件の概要。
2. 今回の起点場所。登録候補がない場合は「AIが補完」と表示する。
3. 編集可能な日本語説明。
4. 「反映」「別案を作る」「キャンセル」。

固定条件と起点場所は参照表示に留める。固定条件を変える場合はプレビューを閉じて通常画面で選択し直す。起点場所は説明編集で変更できる。

「反映」中も説明を保持し、成功時だけ選択状態を更新して現在のpositive／negative出力を新しい結果で置き換える。調整があれば調整後の説明へ置き換え、「固定中の服装を優先したため、説明内の服装を修正しました」のように、対象と理由を表示する。失敗時は説明と元の画面状態を保持する。

反映結果にはF20と同様に、人物LoRAタグとトリガーを後から識別して差し替えられる出力元メタデータを持たせる。一時候補や既存項目由来の本文を人物差し替えで失わない。

## プライバシー、ログ、保持

実データを開発確認へ使用しない。テストは架空の固定条件、場所、説明、外部LLM Fakeだけを使う。

通常ログへ固定条件の名前・文面、日本語説明、起点場所の文面、一時候補、positive／negative、System Prompt、LLMの生応答を記録しない。追跡ID、結果分類、候補件数、モデル名、処理時間、エラー種別だけを記録できる。

日本語案、編集内容、解析結果は生成履歴としてDBへ保存しない。画面上の作業状態だけに保持し、ページ終了後の復元は対象外とする。

## 失敗時の振る舞い

- 場所候補一覧の取得に失敗した場合は候補なしと誤認せず、生成を開始しない。
- 日本語案生成に失敗した場合は固定条件と既存出力を維持し、再試行を案内する。
- 反映解析に失敗した場合は編集済み説明とプレビューを維持し、選択と出力を変更しない。
- 応答の一部だけが妥当でも部分反映しない。
- 反映後の一時候補保存に失敗した場合は出力と候補を維持し、保存だけを再試行できる。
- 古い生成・解析応答が後から届いても、現在表示中の案を上書きしない。

## テスト方針

実際の外部LLM、実データ、アップロード済みデータ、ブラウザー自動操作は使用しない。ApplicationポートのFake、固定乱数Fake、HTTP Fake、テストDB、架空fixture、JavaScript DOMテストを使う。

主な検証範囲は次のとおり。

- 複数の場所候補ブロックから一件を抽選でき、表示名変更の影響を受けない。
- 選択済み場所がある場合は抽選せず、複数選択ならすべてを固定条件にする。
- 場所候補がなくてもAI補完として案を生成できる。
- 人物LoRA未選択を許容し、自動選択しない。
- 固定条件を日本語案と反映解析の両方へ渡し、結果から欠落させない。
- 「別案を作る」で未選択の起点場所を引き直す。
- 説明内で起点場所を変更した場合、元の場所を強制しない。
- 既存項目IDだけを選択し、`single`と`multiple`の規則を守る。
- 固定条件との矛盾を調整し、理由を返す。
- 一時候補0件を正常とし、positive／negative、上限件数、ラベル、タグを検証する。
- 登録済み項目がコンテキスト予算を超える場合、LLMを呼ばず選択と出力を維持する。
- 生成・解析・保存の各失敗で元の選択、出力、編集内容を保持する。
- 古い応答と二重送信を防ぐ。
- ログに入力・生成内容・外部応答を含めない。

## 設計判断

- 場所だけを通常の乱数で選び、その後の意味判断はLLMへ任せる。
- 日本語案とプロンプト解析を二段階にし、利用者が完成イメージを編集してから既存選択へ反映する。
- 手動選択は固定条件、乱数で選んだ場所は編集可能な起点として区別する。
- 人物LoRAは任意とし、未選択時に自動選択しない。
- 場所候補はブロック名ではなく複数指定可能な役割で識別する。
- 不足要素は自動保存せず、一時利用と明示保存を分ける。
- 初回はpositive一時候補だけを保存対象とし、negative保存はF16実装後の拡張とする。
- F20の接続基盤とF22の候補保存思想を再利用するが、ユースケースと状態は混同しない。

## 未決事項

初回実装を妨げる未決事項はない。実利用で案の偏り、待ち時間、費用、矛盾の見逃しを確認し、必要なら場所候補の重み、同じ場所での再提案、候補送信件数の削減、モデル変更を別途設計する。
