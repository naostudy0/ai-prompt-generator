# F14 人物LoRAの生成設定

- 関連：[機能概要](../../spec/機能概要.md)、[用語集](../../spec/用語集.md)、[F05](F05-LoRAの登録と選択.md)、[F11](F11-人物LoRAの差し替えコピー.md)、[F12](F12-人物LoRAの系統と系統別デフォルト.md)、[F13](F13-ComfyUIへのキュー送信.md)。

## 目的と背景

人物・キャラクターLoRAごとに適したcheckpoint、sampler、schedulerが異なる。現在はComfyUI側で切り替える手間を避けるため系統内で同じ設定を使っているが、生成結果を比較するたびに手作業で設定を変える必要がある。

系統ごとに利用可能な生成設定を登録し、人物LoRAへ各設定を紐づける。通常送信と人物LoRA差し替え送信では対象人物LoRAの設定をワークフローへ適用し、プロンプトと同時にキューへ追加できるようにする。任意設定として、生成画像の保存先を人物LoRAのファイル名に対応するディレクトリへ切り替える。

## 要件

| ID | 要件 |
| --- | --- |
| F14-R01 | checkpoint、sampler、schedulerの選択肢を系統ごとに登録・編集・削除できる |
| F14-R02 | 人物LoRAの登録・編集時に、所属系統のcheckpoint、sampler、schedulerを一つずつ必須選択できる |
| F14-R03 | 別系統の生成設定を人物LoRAへ設定できない |
| F14-R04 | 使用中の生成設定を削除できず、人物LoRAの設定が欠けない |
| F14-R05 | ComfyUI送信時に対象人物LoRAの三設定を、系統ワークフローの設定済み入力位置へ書き込む |
| F14-R06 | checkpoint、sampler、schedulerは、それぞれ系統ワークフロー内の複数入力位置へ同じ値を書き込める |
| F14-R07 | 保存先入力が系統ワークフローに設定されている場合、`tmp/{人物LoRAのファイル名}`を保存先として書き込む |
| F14-R08 | 保存先入力が未設定、または送信対象の人物LoRAがない場合は、ワークフローJSONの保存先を変更しない |
| F14-R09 | 新規人物LoRAには生成設定の既定選択を設けず、三種類を明示的に選ぶまで保存できない |
| F14-R10 | 衣装LoRAには本機能の生成設定を持たせない |

## 対象範囲

対象は、系統別生成設定選択肢の管理、人物LoRAへの必須紐付け、ComfyUIワークフロー入力マッピング、通常・単独・一括送信への適用、既存人物LoRAの移行である。

対象外は、steps、CFG、denoise、VAE、CLIP、UNET等の追加設定、ComfyUIからの選択肢自動取得、ファイルの実在確認、生成後のファイル移動、衣装LoRA別の生成設定である。

## 業務ルール

### 系統別の選択肢

- 生成設定の種類は`checkpoint`、`sampler`、`scheduler`の三つに限定する。
- 各選択肢は所属系統、種類、ComfyUIへ渡す値を持つ。同じ系統・種類・値の重複は許可しない。
- 値は前後空白を除いた一文字以上とする。ComfyUIが受け付ける値かどうかはキュー送信時の応答で最終確認し、本アプリは外部ファイルの存在を推測しない。
- 選択肢の値を編集すると、それを参照する人物LoRAの次回送信にも新しい値が反映される。人物LoRAごとに文字列を複製しない。
- 人物LoRAが参照中の選択肢は削除できない。別の選択肢へ変更してから削除する。
- 系統削除時はF12どおり使用中の人物LoRAがないことを前提とし、所属する生成設定選択肢も同じ更新単位で削除する。

### 人物LoRAとの対応

- 人物LoRAは、所属系統と同じ系統に属するcheckpoint、sampler、schedulerを一つずつ参照する。
- 人物LoRAの追加・編集では三項目すべてを必須とする。選択肢が一種類でも未登録なら保存できず、先に系統の生成設定を登録するよう案内する。
- 所属系統を変更した場合、旧系統の三選択は無効になる。利用者が新しい系統の三項目を選び直すまで保存できない。
- 衣装LoRAは人物LoRAの生成環境を変更する主体ではないため、三設定を保持しない。

### 保存先ディレクトリ

- 保存先へ設定する値は`tmp/{fileName}`とする。ファイル名は既存仕様どおり拡張子を含めず、LoRAタグにも同じ値を用いる。
- `fileName`はLoRA全体で一意であるため、登録名の重複に左右されず人物LoRAごとのディレクトリを識別できる。
- 本機能は`tmp/`とファイル名を結合し、ワークフローの設定済み入力へJSON文字列として代入する。利用者入力を任意のパスとして解釈せず、既存のLoRAファイル名制約を適用する。
- 保存先入力マッピングは任意とする。未設定なら元JSONの値を維持する。人物LoRA未選択の通常送信も元JSONの値を維持する。

## ユースケース

### 1. 系統へ生成設定選択肢を登録する

- **入力**：系統ID、種類、ComfyUIへ渡す値。
- **事前条件**：対象系統が存在する。
- **正常系**：同じ系統の該当種類へ選択肢を追加し、人物LoRAフォームで選べるようにする。
- **例外**：空値または同一値の重複は422とし、既存データを変更しない。

### 2. 人物LoRAへ生成設定を設定する

- **入力**：既存の人物LoRA項目、所属系統ID、checkpoint選択肢ID、sampler選択肢ID、scheduler選択肢ID。
- **事前条件**：三選択肢が存在し、すべて所属系統と一致する。
- **正常系**：人物LoRAと三参照を同じ更新単位で保存する。
- **例外**：未選択、存在しない選択肢、種類違い、系統違いは422とし、既存LoRAを変更しない。

### 3. 人物LoRAの設定でComfyUIへ送信する

- **入力**：対象人物LoRA、完成したpositive／negative、系統別ワークフロー。
- **事前条件**：人物LoRAの三設定と、系統ワークフローの三種類の入力マッピングが有効である。
- **正常系**：positive、negative、seedに加え、人物LoRAのcheckpointを全checkpoint入力、samplerを全sampler入力、schedulerを全scheduler入力へ代入する。任意の保存先入力があれば`fileName`を代入してキューへ送る。
- **事後条件**：保存済み人物LoRA、選択肢、元ワークフローは変更しない。
- **例外**：設定欠落、入力位置不正、ComfyUI拒否は成功扱いにしない。一括送信では候補単位の失敗として残りを続行する。

通常送信では、現在の出力を作成した人物LoRAを対象とする。人物LoRAを含めずに作成した出力では生成設定と保存先を上書きせず、ワークフロー本来の値を使う。人物LoRA差し替えの単独・一括送信では、各候補の人物LoRA設定を使う。

## 画面設計

系統管理モーダルに、checkpoint、sampler、schedulerの選択肢管理を置く。種類ごとに登録済み値を一覧表示し、追加・編集・削除できるようにする。人物LoRAフォームでは所属系統を先に選び、その系統の三一覧をプルダウンで表示する。候補がない種類には「系統管理で先に登録してください」と表示し、保存操作を無効にする。

ComfyUIワークフロー設定には次の入力マッピングを追加する。

| 役割 | 件数 | 必須 | 設定値 |
| --- | --- | --- | --- |
| checkpoint | 一件以上 | 必須 | 人物LoRAが参照するcheckpoint値 |
| sampler | 一件以上 | 必須 | 人物LoRAが参照するsampler値 |
| scheduler | 一件以上 | 必須 | 人物LoRAが参照するscheduler値 |
| output directory | 0件または1件 | 任意 | `tmp/{人物LoRAのfileName}` |

複数入力は行の追加・削除で設定する。各行はノードIDと入力名の組を持つ。同じ役割内の同一組は重複登録できない。ワークフロー保存時に全入力の存在と現在値の型を検証する。checkpoint、sampler、scheduler、output directoryはいずれも文字列入力を必要とする。

## API・アプリケーション設計

### 系統別生成設定

- `GET /model-families/{family}/generation-setting-options`：三種類の選択肢を返す。
- `POST /model-families/{family}/generation-setting-options`：種類と値を登録する。
- `PUT /generation-setting-options/{option}`：値を変更する。所属系統と種類は変更しない。
- `DELETE /generation-setting-options/{option}`：未使用の場合だけ削除する。

更新は目的ごとの`Writes`、一覧取得は`Queries`へ置く。人物LoRA保存APIには`checkpointOptionId`、`samplerOptionId`、`schedulerOptionId`を追加する。参照APIは人物LoRAごとに三IDと表示値を返し、ブラウザーが系統別選択肢との対応を復元できるようにする。

ComfyUI送信のApplication入力には人物LoRA IDを追加する。サーバー側で人物LoRAと三設定を取得し、ブラウザーが送信したcheckpoint文字列等を信用しない。人物LoRA差し替え候補でもcandidate keyだけでなく人物LoRA IDを送り、候補の所属系統と設定を再取得する。これにより通常送信、一件送信、一括送信で同じ保存済み設定を使用する。

## 永続化と整合性

生成設定選択肢は、ID、model family ID、種類、値、timestampsを保持する。`model_family_id + kind + value`へ一意制約を置く。人物LoRAのレコードには三つの選択肢IDを外部キーとして追加する。衣装LoRAでは三列をNULLとし、用途に応じた必須・禁止ルールをDomain/Applicationで保証する。

DBの外部キーだけでは選択肢の種類と系統一致を保証できないため、人物LoRA保存ユースケースが三選択肢をまとめて取得して検証する。選択肢削除は参照中なら競合として拒否し、人物LoRA更新との競合でも不正参照を残さない。

ComfyUIワークフローのマッピングは、既存の単一マッピング列を増やし続けず、ワークフローに属する役割・ノードID・入力名の子レコードとして保持する。positive、negative、seed、checkpoint、sampler、scheduler、output directoryを同じ表現で扱い、役割ごとの件数制約は保存ユースケースで保証する。

## 既存データの移行

新規人物LoRA登録には既定選択を設けない。一方、既存人物LoRAを必須参照へ移行するため、次の選択肢を各既存人物LoRAの所属系統へ用意して割り当てる。

| 種類 | 移行値 |
| --- | --- |
| checkpoint | `waiIllustriousSDXL_v90.safetensors` |
| sampler | `euler_ancestral` |
| scheduler | `normal` |

同一系統では選択肢を一件ずつ共有し、LoRAごとに重複作成しない。既に同じ値がある場合は再利用する。衣装LoRAには割り当てない。移行後に人物LoRAの三参照がすべて有効であることを検証してから必須制約を有効にする。

この移行値は既存データを有効な状態にするためだけのものであり、新規フォームの初期選択や将来追加する系統の既定値にはしない。

## 設計判断

- 自由入力で人物LoRAごとに同じ文字列を複製せず、系統別の選択肢を参照する。入力ミスを減らし、同じ設定値の変更箇所を一つにするためである。
- ComfyUIのノードIDや入力名を人物LoRAへ持たせず、系統ワークフローへ持たせる。人物LoRAの意味とワークフロー構造の変更理由を分離するためである。
- checkpoint、sampler、schedulerは複数入力を許可する。初回生成と描き直し等の複数ノードを同じ設定へ揃え、ワークフロー差異へ対応するためである。
- 保存先マッピングだけを任意とする。保存ノードがないワークフローや、JSON既定値を維持したい運用を許容するためである。
- 出力先には登録名でなく一意な`fileName`を使う。登録名は重複可能でディレクトリの識別に適さないためである。

## 未決事項・将来候補

- `tmp/`以外の接頭辞や保存先テンプレートを系統設定に持たせる機能は、今回の範囲に含めない。
- ComfyUIから利用可能なcheckpoint、sampler、schedulerを同期する機能は、手動登録の運用負担が問題になった時点で設計する。
- 人物LoRA設定をお気に入りへスナップショット保存する機能は含めず、送信時点の最新設定を使用する。
