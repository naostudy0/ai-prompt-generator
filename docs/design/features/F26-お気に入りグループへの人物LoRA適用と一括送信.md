# F26 お気に入りグループへの人物LoRA適用と一括送信

- 関連：[機能概要](../../spec/機能概要.md)、[用語集](../../spec/用語集.md)、[F04](F04-お気に入りプロンプト.md)、[F05](F05-LoRAの登録と選択.md)、[F13](F13-ComfyUIへのキュー送信.md)、[F21](F21-人物LoRA差し替えグループ.md)

## 目的と背景

利用者が構図や場面として再利用したい複数のお気に入りへ同じ人物LoRAを適用し、お気に入りを一件ずつ呼び出して差し替えることなくComfyUIへまとめて送信できるようにする。

お気に入りはF04のpositive／negative一組を表す既存形式のままとする。用途ごとにチェックしたお気に入りID集合を名前付きグループとして同じブラウザーへ保存し、現在選択中の人物LoRA・所属トリガー・強度を送信時だけ適用する。

## 要件

| ID | 要件 |
| --- | --- |
| F26-R01 | お気に入り一覧から複数のお気に入りをチェックできる |
| F26-R02 | 現在のチェック集合へ名前を付け、同じブラウザーで保存・呼び出し・削除できる |
| F26-R03 | グループ呼び出しで現在のチェックを保存内容へ置き換え、その後の変更は明示的な上書きまで保存済みグループへ反映しない |
| F26-R04 | 通常画面で現在選択中の人物LoRA、所属トリガー、強度を一括処理開始時に固定して各お気に入りへ適用できる |
| F26-R05 | 人物LoRAを含むお気に入りでは保存済み人物LoRAタグとトリガーだけを安全に差し替えられる |
| F26-R06 | 人物LoRAを含まないお気に入りでは人物LoRAタグとトリガーを既存のpositiveセクション順へ挿入できる |
| F26-R07 | negative、衣装LoRA、服装、その他の文面とお気に入り本体を変更しない |
| F26-R08 | 準備できた1件以上100件以下を確認後にComfyUIへ一括送信できる |
| F26-R09 | 差し替え不能な項目と送信失敗を個別に示し、一件の失敗後も残りを処理できる |
| F26-R10 | 結果不明の送信を自動再送せず、利用者へComfyUIキュー確認を案内できる |

## 対象範囲

お気に入り一覧のチェック、全選択・全解除、名前付きグループの保存・呼び出し・削除、人物LoRAの差し替えまたは挿入、一括送信確認、項目別結果表示を対象とする。

シナリオや複数場面を持つお気に入り形式、グループのDB保存・端末間同期・共有・並べ替え・改名・複製、お気に入り本体の更新、衣装LoRAやオプションの一括差し替えは対象外とする。

## チェック状態とグループ

初回の現在チェックは全件未選択とする。チェック変更、全選択、全解除は取得済みのお気に入り全体へ適用する。現在チェックと名前付きグループは別の`localStorage`キーへバージョン1のJSONとして保存し、プロンプト本文、画像、表示名、LoRA名を含めない。

候補は`favorite:{お気に入りID}`形式のお気に入り候補キーで照合する。文字列から復元したIDをサーバー用の業務IDとして信用せず、一覧・詳細APIが返したお気に入りIDを使用する。

グループ名は前後空白を除いた1文字以上100文字以下とする。大文字小文字を区別しない同名保存は確認後に上書きする。空のチェック集合も保存できる。呼び出しは現在チェックを完全に置き換え、削除済みのお気に入りは除外して不足件数を通知する。新規お気に入りを自動選択しない。

`localStorage`を読めない場合は未選択から開始する。書き込めない場合も画面内のチェックと一括送信は継続できる。グループ書き込み失敗時はメモリ上のグループも操作前へ戻す。

## 人物LoRAの適用

一括処理開始時に、通常画面で現在選択中の人物LoRA ID、所属トリガーIDまたは未選択、強度、表示用情報を一度取得して固定する。人物LoRAが未選択なら開始しない。

各お気に入りの詳細と現在のLoRA候補を照合する。保存時に人物LoRAがあった場合は、保存済みID・強度・トリガーから元タグと文面を構築し、完成済みpositive内で各範囲を一意に特定する。元LoRAタグまたは保存済みの元トリガーを一意に特定できない、IDが削除済み、所属関係が不正な場合は、そのお気に入りを除外する。推測による置換や隣接追記を行わない。

保存時に人物LoRAがなかった場合は、選択中の人物LoRAタグとトリガーを、デフォルトの後かつ衣装LoRA・服装・オプションより前の人物LoRAセクションへ挿入する。デフォルトが空ならpositiveの先頭へ挿入する。

適用処理は送信用の一時値だけを作り、保存済みpositive／negative、選択スナップショット、選択概要を更新しない。

## ComfyUI一括送信

適用人物LoRAの所属系統と、そのLoRAに登録されたcheckpoint、sampler、scheduler、保存先設定を全項目へ使用する。お気に入り保存時の人物LoRA系統・生成設定は使用しない。

送信前に全詳細を取得して差し替え・挿入可否を判定する。準備成功0件ではAPIを呼ばない。1件以上では人物LoRA名、トリガー名または未選択、強度、準備成功件数、除外件数を表示し、承認後だけ送信する。

既存`POST /comfyui/prompts/batch`を使用し、一回の送信は1件以上100件以下とする。100件を超える場合は自動分割せず、チェックを減らすよう案内する。送信順はお気に入り一覧APIの順序とする。

一件の送信失敗後も残りを処理し、成功・失敗・結果不明をお気に入り名へ対応付けて表示する。応答前の通信失敗やタイムアウトで結果が不明な場合は自動再送しない。

## 画面

「お気に入りを開く」モーダルで、グループ選択・呼び出し・削除、グループ名入力・現在チェックの保存、全選択・全解除、選択件数、適用人物LoRAの概要、一括送信ボタンをお気に入りカードより前に表示する。各カードのチェックは呼び出し、編集、削除と独立させる。

一覧未取得、人物LoRA未選択、選択0件、一括処理中は状況に応じて送信を無効にする。一括処理中はチェック、グループ、編集、削除、モーダル終了を無効にし、二重送信を防ぐ。

## APIと実装境界

- `GET /favorite-prompts`で一覧と順序、`GET /favorite-prompts/{favoritePrompt}`で完成プロンプトと選択スナップショットを取得する。
- `GET /lora-prompt-options`の取得済み結果で、保存時と現在の人物LoRA・トリガーを照合する。
- `POST /comfyui/prompts/batch`の既存入力・部分失敗結果を利用する。候補キーは結果対応用の不透明な文字列として扱う。
- グループ用API、DBマイグレーション、Laravelのグループモデルを追加しない。
- グループの検証・集合計算とプロンプト適用はDOMから分離したJavaScript純粋関数へ置く。
- サーバー側は既存どおりLoRA、系統、生成設定、ワークフローの整合性を保証する。

## 失敗時

- 一覧取得失敗ではチェックやグループを削除せず、送信しない。
- 詳細取得または安全な適用に失敗したお気に入りは除外し、残りの準備を続ける。
- 適用人物LoRAが未選択・削除済み・非表示・生成設定不正の場合は一件も送信しない。
- ワークフロー未設定・不正の場合は項目別失敗として表示し、既存一括送信の継続規則に従う。
- 一括通信全体の結果が不明な場合は、再送せずComfyUIキュー確認を案内する。

## 受入条件

| 要件 | 前提・操作 | 期待結果 |
| --- | --- | --- |
| R01・R02・R03 | 複数のお気に入りをチェックしてグループ保存し、再読み込み後に呼び出す | 同じブラウザーで保存集合へチェックが置き換わる |
| R02 | 削除済みお気に入りを含むグループを呼び出す | 利用可能な項目だけが選ばれ、不足件数が表示される |
| R04・R05 | 人物LoRAとトリガーを含むお気に入りへ別の現在選択を適用する | 元LoRA・トリガーだけが現在選択と強度へ差し替わる |
| R04・R06 | 人物LoRAなしで保存したお気に入りへ現在選択を適用する | デフォルト後の人物LoRAセクションへタグとトリガーが挿入される |
| R05・R09 | 保存済みトリガーが手編集または重複で一意に特定できない | そのお気に入りだけが除外され、推測置換されない |
| R07 | 一括適用する | negative、衣装LoRA、服装、その他文面、お気に入り本体が変わらない |
| R08 | 1〜100件を準備して確認を承認する | 一覧順で一回の一括APIへ送信される |
| R08 | 101件を準備する | APIを呼ばず、100件以下へ減らす案内が表示される |
| R08 | 確認を取り消す | ComfyUIへ送信されない |
| R09・R10 | 一件失敗または結果不明を含む応答を受ける | 残りを処理し、項目別結果を示し、自動再送しない |
| R02 | `localStorage`が利用できない | 失敗を通知し、画面内のチェックと送信を継続できる |

## 検証

グループとチェックは架空IDとFake Storage、人物LoRA適用は架空プロンプトの純粋関数テスト、画面操作はJSDOMとFake fetch、HTTP境界はテストDBとFake ComfyUIで検証する。実ブラウザー、実DB内容、アップロード済みデータ、実ComfyUIは確認に使用しない。

## 未決事項

実装開始を妨げる未決事項はない。端末間同期、グループの並べ替え・改名・複製は別機能として設計する。
