# F23 AIシナリオプロンプト生成

関連文書：[機能概要](../../spec/機能概要.md)、[用語集](../../spec/用語集.md)、[アーキテクチャ](../アーキテクチャ.md)、[画面設計](../画面設計.md)、[F20 AIプロンプト生成](F20-AIプロンプト生成.md)、[F11 人物LoRAの差し替えコピー](F11-人物LoRAの差し替えコピー.md)、[F13 ComfyUIへのキュー送信](F13-ComfyUIへのキュー送信.md)、[外部LLM連携の境界](../../decisions/0005-外部LLM連携の境界.md)

## 目的と背景

利用者は、登山など時間の流れを持つ題材から、目的地へ向かう、到着する、行動する、到達するという一連の場面を複数枚の画像として準備したい。一枚ずつ独立して指示すると流れが抜けたり、人物、服装、画風などが意図せず変わったりするため、先に全体のシナリオを確認し、その流れと継続性を踏まえた画像生成用プロンプトをまとめて得る。

利用者はAIが作った流れをそのまま受け入れるのではなく、場面の追加・削除・並べ替え・編集を行う。人物、服装、画風などは基本的に前場面から固定し、必要な場面だけ利用者が変更を指定する。生成結果は一場面ずつ既存出力へ反映し、既存画面でLoRA設定と微調整を行う。

## 要件とスコープ

| ID | 要件 |
| --- | --- |
| F23-R01 | シナリオの元になる説明と場面数から、指定件数の順序付きシナリオ案を生成できる |
| F23-R02 | 場面数は3〜10とし、初期値を5とする |
| F23-R03 | 生成した場面のタイトル、説明、変更内容、全体の継続性メモを編集できる |
| F23-R04 | 場面を3〜10件の範囲で追加・削除・並べ替えできる |
| F23-R05 | 変更指示がない場面は人物、服装、画風などを前場面から引き継ぎ、変更指示がある場面は指定項目だけを変えるようLLMへ指示する |
| F23-R06 | 確定した全場面から、入力順と対応するpositive／negative候補をまとめて生成できる |
| F23-R07 | 前後の文脈を保ったまま、指定した一場面だけを再生成できる |
| F23-R08 | 各候補を編集し、一場面ずつ明示操作で既存出力へ反映できる |
| F23-R09 | 反映時に選択中の人物LoRAとトリガーをAIに改変させず、F20と同じ規則で既存出力へ合成する |
| F23-R10 | 入力、シナリオ案、正常な生成結果を、別の処理の失敗によって失わない |
| F23-R11 | シナリオ、場面、生成結果をDB、永続ストレージ、通常ログへ保存しない |
| F23-R12 | 二重送信、古い応答による上書き、自動再試行による重複生成を防ぐ |

初回範囲は、シナリオ生成用大型モーダル、シナリオ案生成、全場面のプロンプト生成、一場面の再生成、一場面ずつの既存出力への反映とする。

生成履歴、再読み込み後の復元、複数タブ共有、シナリオのDB・ファイル・`localStorage`保存、全場面の一括反映、全場面の一括ComfyUI送信、LoRAの一括設定、F22のタグ候補保存、Queueによる非同期化は対象外とする。LoRA調整、手編集、コピー、クリップ、お気に入り、ComfyUI送信は、一場面を既存出力へ反映した後に既存機能で行う。

## ユースケース

### シナリオ案を生成して編集する

- **実行者**：認証のない個人利用環境の利用者。
- **入力**：シナリオの元になる説明、3〜10の場面数、プロンプト形式。
- **事前条件**：Laravel実行環境から設定済みの外部LLM APIへ到達できる。
- **正常な流れ**：利用者が説明と場面数を入力する。ApplicationがLLMへシナリオ案の作成を依頼し、継続性メモと指定件数の場面を返す。利用者は継続性メモと各場面のタイトル、説明、変更内容を編集し、場面を追加・削除・並べ替える。
- **出力・事後条件**：3〜10件の編集済みシナリオ案がブラウザー内に保持される。既存出力と保存済みデータは変更しない。
- **例外の流れ**：入力不正は該当項目に理由を示す。外部連携の失敗は入力を保持し、明示的な再試行を案内する。不完全なAI応答は採用しない。

### 全場面の画像プロンプトを生成する

- **実行者**：シナリオ案を編集した利用者。
- **入力**：元の説明、継続性メモ、順序付き場面、プロンプト形式。
- **事前条件**：場面が3〜10件で、各場面に一時ID、タイトル、説明がある。
- **正常な流れ**：Applicationが編集済みシナリオ全体をLLMへ渡す。LLMは順序と継続性を踏まえ、各一時IDに対応するpositive／negativeを返す。Applicationは件数、順序、ID、各値を検証し、全件が有効な場合だけ結果を返す。
- **出力・事後条件**：全場面の編集可能な候補とモデル・生成時間が表示される。既存出力は変更しない。
- **例外の流れ**：一件でも欠落、重複、余分な結果、不正型、空positiveがあれば応答全体を不正として扱い、編集済みシナリオを保持する。

### 一場面を再生成して既存出力へ反映する

- **実行者**：場面別候補を確認する利用者。
- **入力**：シナリオ全体、現在の全場面候補、対象場面の一時ID、対象への最新指示、プロンプト形式。
- **事前条件**：対象IDが現在のシナリオに一件だけ存在する。
- **正常な流れ**：前後の場面を文脈として対象場面だけをLLMで再生成する。利用者は候補を編集し、「既存出力へ反映」を実行する。F20と同じ合成規則で選択中のデフォルトと人物LoRAセクションを加え、positive／negative出力を置き換える。
- **出力・事後条件**：対象外の候補とシナリオを保持する。反映後は既存のLoRA調整、手編集、コピー、クリップ、お気に入り、人物LoRA差し替え、ComfyUI送信を利用できる。
- **例外の流れ**：再生成失敗時は対象場面の現在の候補を保持する。上書き再生成と未反映内容を持つモーダル終了は利用者へ確認する。

## 業務ルール

### 入力と場面数

- 元の`description`は必須の文字列とし、前後の空白を除いて1文字以上2,000文字以下とする。既存F20と同じ上限にして過大な入力と待ち時間を抑える。
- `sceneCount`は3以上10以下の整数とし、画面の初期値を5とする。3は流れを表す最小限の開始・展開・到達を想定し、10は同期通信の待ち時間と確認負荷を抑える初期限界である。
- `promptStyle`はF20と同じ`danbooru_tags`または`natural_language`とし、初期値を`danbooru_tags`とする。
- 編集後も場面は3〜10件とする。3件のときは削除できず、10件のときは追加できない。

### シナリオ案と継続性

- シナリオ案は元の説明、編集可能な継続性メモ、順序付き場面からなる。
- 各場面はブラウザーで生成した作業中だけ有効な一時ID、タイトル、説明、`changesFromPrevious`を持つ。一時IDは並べ替え後も変えない。
- シナリオ案生成時、LLMは元の説明から全場面で維持すべき人物、服装、画風等を継続性メモとして抽出する。ただし利用者は生成後に修正できる。
- `changesFromPrevious`が空なら、継続性メモと前場面で確定した要素を引き継ぐようLLMへ指示する。値がある場合は指定された内容だけを変更し、指定外の要素を維持するよう指示する。
- 最初の場面の`changesFromPrevious`は、前場面との差分ではなく開始時点の人物、服装、画風等の補足として扱う。
- 場面の追加、削除、並べ替え、編集後は、表示順をシナリオ上の順序として全場面生成へ渡す。

### 生成結果と既存出力

- 全場面生成は、入力場面と同じ件数、同じ一時ID、同じ順序の候補だけを成功とする。
- 各候補は空でないpositive、空を許容するnegative、場面一時IDを持つ。
- 全場面生成後のpositive／negativeはブラウザー内で編集できる。編集はシナリオ案や他場面へ自動反映しない。
- 個別再生成は対象外の候補を変更しない。対象場面の現在の手編集結果を上書きする前に確認する。
- 「既存出力へ反映」は一場面に対して行い、F20のデフォルトと人物LoRAの合成規則、出力元メタデータ、人物LoRA差し替え規則を再利用する。衣装LoRA、服装、オプション項目を自動合成しない。
- 反映してもモーダルと他場面の候補を閉じたり削除したりしない。利用者はLoRA等を調整した後、モーダルへ戻って次の場面を反映できる。

## ドメインとApplication設計

本機能は保存する業務状態や複数利用者間の整合性を持たないため、新しい集約、Repository、DBテーブルは設けない。編集途中のシナリオはフロントエンドの作業状態である。Applicationは外部AI呼び出しの手順、入力と応答の対応、失敗時の非反映を保証する。

外部通信と計測という副作用を伴うため、返値だけを返す処理でもすべて`Writes`へ置く。

| 単位 | 責務 |
| --- | --- |
| `PlanIllustrationScenario` | 元の説明と場面数から継続性メモと場面案を生成する |
| `GenerateScenarioPrompts` | 編集済みの全場面を一括生成し、件数・順序・ID対応を検証する |
| `RegenerateScenarioScenePrompt` | 全体を文脈として対象場面だけを再生成する |
| `IllustrationScenarioPlanner` | 外部LLMへシナリオ案を要求するApplicationポート |
| `ScenarioIllustrationPromptGenerator` | 全場面または対象場面の候補を要求するApplicationポート |
| 入出力DTO | ApplicationへHTTPや外部SDKの型を持ち込まず、シナリオ、場面、候補を不変な型で受け渡す |

実装時は各Write配下にInput、Handler、Resultを必要な分だけ置く。シナリオ案と候補のDTOは複数ユースケースで同じ意味と制約を共有する場合だけ`Application/PromptPreparation/DTO`へ置く。

## HTTP API

既存画面からの操作であるため、`routes/web.php`にWebミドルウェアとCSRF保護を使う同一オリジンJSONエンドポイントを定義する。

| メソッドとURL | 目的 | 成功レスポンス |
| --- | --- | --- |
| `POST /illustration-scenarios/plan` | シナリオ案を生成する | 継続性メモ、指定件数の場面、モデル、生成時間 |
| `POST /illustration-scenarios/prompts` | 全場面の候補を生成する | 入力と同順の場面ID・positive・negative、モデル、生成時間 |
| `POST /illustration-scenarios/scenes/prompt` | 一場面を再生成する | 対象場面ID・positive・negative、モデル、生成時間 |

全場面生成のリクエスト例：

```json
{
  "description": "登山へ出発し、山頂へ到達するまで",
  "continuityNotes": "同じ成人女性、赤い登山服、写実的な画風を維持する",
  "promptStyle": "danbooru_tags",
  "scenes": [
    {
      "id": "scene-1",
      "title": "出発",
      "description": "朝、自宅から登山へ出発する",
      "changesFromPrevious": ""
    },
    {
      "id": "scene-2",
      "title": "登山口",
      "description": "登山口へ到着して山を見上げる",
      "changesFromPrevious": "場所を登山口へ変更する"
    },
    {
      "id": "scene-3",
      "title": "山頂",
      "description": "山頂へ到達して景色を眺める",
      "changesFromPrevious": "防寒着を追加する"
    }
  ]
}
```

成功レスポンス例：

```json
{
  "scenes": [
    {
      "id": "scene-1",
      "positivePrompt": "1woman, red hiking jacket, leaving home, morning",
      "negativePrompt": "low quality, blurry"
    },
    {
      "id": "scene-2",
      "positivePrompt": "1woman, red hiking jacket, trailhead, looking up at mountain",
      "negativePrompt": "low quality, blurry"
    },
    {
      "id": "scene-3",
      "positivePrompt": "1woman, red hiking jacket, winter outerwear, mountain summit, panoramic view",
      "negativePrompt": "low quality, blurry"
    }
  ],
  "model": "configured-model",
  "promptStyle": "danbooru_tags",
  "generationTimeMs": 6200
}
```

HTTP入口は説明、件数、配列、文字数、許可値を検証する。場面タイトルは1〜100文字、場面説明は1〜1,000文字、変更内容は0〜1,000文字、継続性メモは0〜2,000文字、一時IDは1〜100文字とし、リクエスト内で一意でなければならない。これらは同期通信の入力規模と画面での確認負荷を制限するための初期上限である。

## 外部LLM連携

InfrastructureのOllama Chat API互換アダプターから、既存F20と同じサーバー側設定を使って`POST /api/chat`を非ストリーミングで呼ぶ。用途別System Promptはシナリオ案、全場面候補、個別再生成を分け、PHPコード内の長文リテラルにしない。

構造化出力のJSON Schemaで次を制約する。

- シナリオ案は編集可能な`continuity_notes`と、指定件数の`title`・`description`・`changes_from_previous`を返す。
- 全場面候補は入力と同じ件数の`id`・`positive_prompt`・`negative_prompt`を返す。
- 個別再生成は対象の`id`・`positive_prompt`・`negative_prompt`だけを返す。
- 説明文、Markdown、コードフェンス、余分なキーを返さない。

全場面生成では、元の説明、継続性メモ、編集済みの全場面を送る。個別再生成では、それらに加えて現在の全場面候補、対象ID、対象場面への最新指示を送る。一時IDは応答対応のためだけに使い、物語上の意味を持たせない。

接続先、モデル、タイムアウト、最大生成トークン数は既存のサーバー側設定を使う。3〜10場面の生成量で不足する場合は、利用者入力ではなく用途別の設定値として最大生成トークン数を追加する。

## 失敗、競合、再試行

| 失敗 | ステータス | 利用者への扱い |
| --- | --- | --- |
| 必須、文字数、件数、ID重複、形式の入力不正 | 422 | 該当項目と修正理由を示し、入力を保持する |
| 接続失敗、タイムアウト、上流HTTPエラー | 503 | 一時的に利用できないことを示し、明示再試行を案内する |
| 不正JSON、必須キー欠落、不正型、件数・順序・ID不一致、空positive | 502 | 不正な結果を一部採用せず、明示再試行を案内する |
| System Prompt読み込み失敗等の内部障害 | 500 | 内部情報を返さず処理失敗を示す |

自動再試行は待ち時間と二重生成を増やすため行わない。外部AI呼び出し中にDBトランザクションを開始しない。

フロントエンドは処理中の該当操作を無効化する。処理単位ごとのリクエストトークンと`AbortController`を使い、後から開始した操作、利用者の編集、モーダル終了後に古い応答を反映しない。全場面生成の失敗は編集済みシナリオを保持し、個別再生成の失敗は現在の対象候補を保持する。

## 画面とフロントエンド

既存画面に「シナリオを作成」ボタンを置き、F20とは別の大型モーダルを開く。モーダルは次の3段階を持つ。

1. **シナリオ入力**：元の説明、場面数、プロンプト形式、シナリオ案生成ボタン。
2. **シナリオ編集**：継続性メモと場面カード。追加、削除、ドラッグと上下操作による並べ替え、各項目の編集、全場面生成ボタン。
3. **プロンプト確認**：場面ごとの編集可能なpositive／negative、モデルと生成時間、個別再生成、既存出力への反映。

ドラッグ以外にも上下ボタンを用意し、キーボード操作だけで並べ替えられるようにする。現在の段階、生成中、成功、入力エラー、通信失敗をテキストでも伝える。

`resources/js/illustration-scenario-generator.js`はモーダルの作業状態、場面操作、通信、応答検証、候補編集を担当する。既存出力への反映はF20と共通の公開関数へ、現在のデフォルト、人物LoRA出力元、出力置換を渡す。新モジュールから既存画面の内部変数を直接操作しない。

未反映または未保存ではなく「モーダルを閉じると失われる編集・生成結果」がある状態で閉じる場合は、破棄確認を行う。反映済みの場面があっても他場面の作業状態が残る限り同じ扱いとする。ページ再読み込み時の警告や復元は対象外とする。

## 永続化、ログ、情報の扱い

シナリオの元の説明、継続性メモ、場面、生成候補、個別再生成指示、性能指標をDB、ファイルストレージ、`localStorage`へ保存しない。新しいマイグレーション、Repository、トランザクションは不要である。

通常ログには追跡ID、処理種別、結果分類、モデル、Laravelが実測した時間、上流が返す数値指標だけを記録する。入力全文、System Prompt全文、シナリオ本文、生成したpositive／negative、上流の生レスポンス、場面タイトルを記録しない。

## テスト方針

実際の外部LLM、実際のDB内容、アップロード済みデータを使用しない。ApplicationはポートのFake、InfrastructureとHTTP入口はLaravel HTTPクライアントのFake、フロントエンドは架空データによるJavaScript DOMテストで検証する。ブラウザー自動操作とスクリーンショット確認は行わない。

主な検証範囲は次のとおり。

- 説明の1文字、2,000文字、2,001文字と、場面数の2、3、5、10、11。
- シナリオ案の指定件数、継続性メモ、場面値の変換と不正応答の拒否。
- 場面の追加、削除、上下移動、ドラッグ相当の並べ替え、編集と一時IDの維持。
- 変更指示が空の場合の継続指示と、値がある場合の指定項目だけを変える指示。
- 全場面生成の件数、順序、ID一致と、欠落、重複、余分な結果の拒否。
- 個別再生成へ全体文脈を渡すことと、対象外候補の不変。
- 入力不正、接続失敗、タイムアウト、上流HTTP、不正JSON、不正型、空positive。
- 二重送信防止、中断、古い応答の破棄、失敗時の入力・現在結果の維持。
- 候補編集、上書き確認、破棄確認、一場面ずつの反映。
- F20と同じデフォルト・人物LoRA合成、人物LoRA差し替え、既存機能への受け渡し。
- 通常ログに入力・シナリオ・生成本文が含まれないこと。

## 受入条件と検証

| 要件 | 前提／操作 | 期待結果 |
| --- | --- | --- |
| R01・R02 | 架空の登山説明を入力し、初期値のまま生成する | 継続性メモと5件の順序付き場面案が表示される |
| R02・R04 | 3件の案から削除、10件の案へ追加を試みる | 3件未満への削除と10件超への追加ができない |
| R03・R04 | 場面を追加・編集・並べ替えて全場面生成する | 編集後の値と表示順が、一時IDを保ったままAPIへ渡る |
| R05 | 変更内容を空にした中間場面を生成する | 継続性メモと前場面の要素を維持する指示がLLMへ送られる |
| R05 | 「防寒着を追加」と指定した場面を生成する | 防寒着だけを変更し、指定外の人物・画風等を維持する指示が送られる |
| R06 | 編集済みの5場面を全場面生成する | 入力と同じ件数・順序・IDのpositive／negative候補が表示される |
| R06・R10 | Fakeが一場面を欠落または重複させる | 502となり、部分結果を採用せず編集済みシナリオを保持する |
| R07・R10 | 3番目の場面だけを再生成する | 1、2、4、5番目の候補を変更せず、失敗時は3番目の現在値も保持する |
| R08・R09 | 一場面を編集して既存出力へ反映する | 編集済み候補、選択中デフォルト、人物LoRA・トリガーがF20と同じ規則で合成される |
| R08 | 一場面を反映した後に別場面を選ぶ | モーダル内のシナリオと全候補が残り、次の場面を個別に反映できる |
| R10・R12 | 生成中に再操作、編集、またはモーダル終了を行う | 二重送信をせず、古い応答が新しい状態を上書きしない |
| R11 | 成功と失敗をログ記録する | 追跡・性能項目は残り、入力、場面、生成本文、場面タイトルは含まれない |
| R11 | モーダルを閉じ、ページを再読み込みする | シナリオと候補は復元されず、DB・ファイル・`localStorage`にも保存されない |

プログラムが保証するのは、入力制約、順序とIDの対応、LLMへ渡す継続・変更指示、応答検証、失敗時の非反映である。物語の自然さ、画像間の視覚的一貫性、生成画像の品質は決定的に保証できないため、利用者によるシナリオ編集、候補編集、個別再生成で補う。

## 設計上の判断と未決事項

- 一段階でシナリオと全候補を作らず、シナリオ案を確認してから候補を生成する二段階方式を採用する。不要な流れのまま高コストな複数候補を生成することを避けるためである。
- 場面ごとに独立したAI呼び出しを標準にせず、全場面を一括して生成する。全体の流れと継続性を一つの文脈で扱い、呼び出し回数を抑えるためである。局所的な修正には個別再生成を使う。
- 継続性は基本固定とし、場面ごとの差分を利用者が指定する。全項目を場面ごとに再入力する負担と、AIによる意図しない変更を抑えるためである。
- 作業状態は永続保存しない。初期版の目的は複数場面の下書きを一つずつ既存の調整フローへ渡すことであり、履歴管理や再開は別の利用目的だからである。
- F20の単一生成は短い直接生成経路として残し、F23から内部ユースケースとして呼び出さない。入力と応答の契約、生成目的、失敗単位が異なるためである。ただし既存出力への合成処理は同じ意味と変更理由を持つため共有する。

実装開始を妨げる未決事項はない。同期通信が3〜10場面で実用的でないと検証された場合に限り、ジョブID、結果取得、キャンセル、再実行時の課金と整合性を含む非同期設計を別途行う。
