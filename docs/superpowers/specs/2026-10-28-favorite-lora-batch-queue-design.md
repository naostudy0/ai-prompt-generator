# お気に入りグループへの人物LoRA適用・ComfyUI一括送信 設計

## 目的

利用者が、構図や場面として再利用したい複数のお気に入りへ同じ人物LoRAを適用し、各お気に入りを一件ずつ呼び出して差し替える手間なくComfyUIへまとめて送信できるようにする。

お気に入りは従来どおりpositive／negative一組を表す。シナリオや複数場面を持つ新しいお気に入り形式は導入しない。用途ごとに選んだ複数のお気に入りIDの集合を、名前付きグループとして同じブラウザーへ保存する。

## ゴール

- お気に入り一覧から複数のお気に入りをチェックできる。
- 現在のチェック集合へ名前を付け、同じブラウザーに保存・呼び出し・削除できる。
- 通常画面で現在選択中の人物LoRA、トリガー、強度を、チェック対象のお気に入りすべてへ適用できる。
- 各お気に入りの保存済み人物LoRAタグと所属トリガーだけを差し替え、negative、衣装LoRA、服装、その他の文面を維持する。
- 差し替えに成功したお気に入りを、選択中人物LoRAの系統・生成設定でComfyUIへ一括送信できる。
- 一部の差し替えまたは送信に失敗しても残りを処理し、項目ごとの結果を確認できる。

## 非ゴール

- お気に入りにシナリオや複数場面を保存すること。
- グループをDB、サーバー内ストレージ、Cookieへ保存すること。
- グループを別ブラウザー・別端末と同期すること。
- お気に入り本体、保存済み選択スナップショット、完成プロンプトを書き換えること。
- 人物LoRA以外の衣装LoRA、服装、オプション項目を一括で差し替えること。
- グループ名の変更、並べ替え、複製、共有、インポート、エクスポート。

## 制約と安全方針

- 完成済みpositive／negativeはお気に入りの保存内容を正本とする。
- 保存時に人物LoRAがあったお気に入りで、その部分を安全に特定できない場合は、推測による文字列置換や追記を行わない。
- ComfyUI送信は外部副作用であり、確認後に開始する。結果不明の失敗を自動再送しない。
- グループにはお気に入りIDと利用者が付けた名前だけを保存し、プロンプト本文、画像情報、LoRA名などは保存しない。
- ブラウザー自動操作、実DB内容、アップロード済みファイルを検証に使用しない。架空データとFake、JSDOMで検証する。

## 検討した方式

### 採用：ブラウザー保存の名前付きチェック集合

お気に入り一覧の現在のチェック状態と、名前付きグループを`localStorage`へ保存する。既存のF21人物LoRA差し替えグループと操作・障害時の考え方をそろえ、サーバー側へグループ用の集約やAPIを追加しない。

利点は、既存のお気に入りや認証の設計を変えずに目的を満たせること、プロンプト本文をブラウザー保存へ複製しないことにある。制約は、グループが同じブラウザーだけで有効なことである。利用者はこの方式を選択した。

### 不採用：グループをDBへ保存

端末間で利用できる一方、利用者アカウントがない現状では所有者と共有範囲が曖昧になる。新しい集約、API、テーブル、削除時の整合性も必要となり、今回の目的に対して範囲が大きい。

### 不採用：お気に入りへ分類タグを付与

検索・分類には発展させやすいが、用途ごとに現在の一括送信対象を切り替える操作とは意味が異なる。お気に入り本体の編集・保存仕様まで変更するため採用しない。

## 用語

- **お気に入り候補キー**：お気に入りを識別する`favorite:{お気に入りID}`形式の文字列。保存データの照合だけに使い、文字列から復元したIDを送信APIへ信用して渡さない。
- **現在のチェック状態**：お気に入り一覧で現在一括処理対象になっている候補キー集合。
- **お気に入りグループ**：グループ名とお気に入り候補キー集合の保存済みスナップショット。
- **適用人物LoRA**：通常画面で一括送信開始時に選択されている人物LoRA、所属トリガー、強度の組。

## 画面と操作

既存の「お気に入りを開く」モーダルへグループ管理と一括送信操作を追加する。

```text
お気に入りグループ
[保存済みグループ ▼] [呼び出す] [削除]
[グループ名________________] [現在のチェックで保存]
[すべて選択] [すべて解除]  選択中 N件

[✓] お気に入りA
[ ] お気に入りB
[✓] お気に入りC

適用する人物LoRA: 現在選択中の名前 / トリガー / 強度
[選択中 N件を人物LoRAへ適用してComfyUIへ送信]
```

- チェックは呼び出し、編集、削除とは独立した操作とする。
- 一覧を読み込めていない間はグループ呼び出しと一括送信を無効にする。
- 人物LoRAが未選択なら一括送信できず、通常画面での選択を案内する。
- 送信前に、対象件数、人物LoRA名、トリガー名または未選択、強度を示して確認する。
- グループの保存・呼び出し・削除、利用不能なお気に入り、差し替え除外、送信結果はモーダル内のステータスへ表示する。
- 一括処理中は再送、グループ呼び出し、チェック変更、対象お気に入りの編集・削除を無効にする。モーダルを閉じる操作も処理完了まで無効にする。

## 現在のチェック状態

- 初めて利用するときは、意図しない大量送信を避けるため全件未選択で開始する。
- チェック変更、すべて選択、すべて解除は取得済みの全お気に入りへ適用し、現在のチェック状態を`localStorage`へ保存する。
- 一覧の再取得後、削除済みIDは現在のチェック状態から除外する。新しいお気に入りは自動選択しない。
- 保存済みグループを呼び出すと、現在のチェック状態をグループ内容へ完全に置き換える。未保存のチェック変更を追加確認はせず置き換える。
- 呼び出したグループ自体は、その後チェックを変更しても明示的に上書き保存するまで変えない。

## グループ管理

グループ名は前後空白を除いた1文字以上100文字以下とする。大文字小文字を区別せず同名と判定し、同名保存は確認後に現在のチェック集合で上書きする。空のグループは「すべて対象外」の状態を用途として保存できる。

削除はグループ名を示して確認した後に行う。グループを削除しても現在のチェック状態は変えない。

削除済みなど、グループ内の候補キーに一致する現在のお気に入りがない場合は、その候補を除いてチェックを復元し、不足件数を通知する。新規追加されたお気に入りは自動選択しない。

保存形式は既存F21と別の`localStorage`キーを使う。

```json
{
  "version": 1,
  "groups": [
    {
      "name": "屋外構図",
      "favoriteKeys": ["favorite:12", "favorite:18"]
    }
  ]
}
```

現在のチェック状態もグループとは別キーへバージョン付きJSONで保存する。読み込み時は外部入力として型、バージョン、名前、候補キー配列を検証する。不正な保存値は使用せず、画面内では未選択から操作を継続する。

`localStorage`への書き込みに失敗した場合、グループ操作はメモリ上も操作前へ戻して失敗を通知する。現在のチェック操作は画面内で継続できるが、再読み込み後に保持されないことを通知する。

## 人物LoRA差し替え

一括送信開始時点の通常画面から、人物LoRA ID、トリガーIDまたは未選択、強度を一度取得し、処理中は固定する。各お気に入りの処理途中に通常画面の選択を再評価しない。

各お気に入りについて詳細を取得し、保存済みpositiveと選択スナップショットを使って次の順序で送信用positiveを作る。

1. スナップショットに保存された人物LoRA ID、強度、トリガーIDを取得する。
2. 現在のLoRA候補から保存時の人物LoRAタグとトリガー文面を構築する。
3. 保存時に人物LoRAがあった場合、保存済みpositive内で人物LoRAタグとトリガー文面が一意に特定できることを確認する。元トリガーが保存されているのに一意に特定できない場合も置換を続けず、厳格に差し替え不能とする。
4. 特定した範囲だけを、適用人物LoRAのタグと現在選択中トリガーの文面へ置き換える。トリガー未選択なら元トリガー範囲を削除する。
5. 保存時に人物LoRAがなかった場合は、現在選択中の人物LoRAタグとトリガー文面を、F05のpositive構成順における人物LoRA・トリガーセクションへ新規挿入する。既存のデフォルト、衣装LoRA、服装、オプション文面は維持する。
6. 保存済みnegativeは変更せず使用する。

保存時に人物LoRAがあったにもかかわらず、人物LoRAタグまたは保存済みトリガー範囲が見つからない、複数候補があり一意でない、保存済みIDが削除済み、所属関係が不正など、安全に差し替えられないお気に入りは送信対象から除外する。保存時に人物LoRAがなかったことは除外理由にせず、構造化されたpositiveセクションの合成処理で新規挿入する。

差し替え処理はお気に入りを更新せず、送信要求を組み立てるための一時値だけを作る。

## ComfyUI一括送信

適用人物LoRAの所属系統を全項目の`modelFamilyId`とし、その人物LoRAに登録されたcheckpoint、sampler、scheduler、保存先設定を使用する。お気に入り保存時の人物LoRA系統や生成設定は使用しない。

送信前の準備段階で、チェック対象のお気に入り詳細を取得して全件の差し替え・挿入可否を判定する。準備できた項目が0件ならComfyUI APIを呼ばない。1件以上なら、準備成功件数と除外件数を確認画面へ示し、利用者が承認した場合だけ一括送信を開始する。

既存APIの上限に合わせ、一回の送信は100件までとする。グループ自体には100件を超えて保存できるが、準備成功項目が100件を超える場合は自動分割せず、チェック対象を100件以下へ減らすよう案内する。複数リクエストへ自動分割すると、途中失敗や結果不明時の再実行範囲が曖昧になるためである。

既存の一括キュー送信APIを拡張または同じApplicationサービスから再利用し、項目ごとに次を渡す。

- ブラウザー表示用・結果対応用のお気に入り候補キー
- 適用人物LoRAの系統IDと人物LoRA ID
- 差し替え後positive
- 保存済みnegative

送信順はお気に入り一覧APIの既存順とし、チェック順やグループ保存順では変えない。各送信のseedは既存F13一括送信と同じ規則を用いる。

一件のComfyUI送信に失敗しても残りを処理する。結果は成功、失敗、結果不明をお気に入り候補キーへ対応付けて返し、画面ではお気に入り名ごとに表示する。タイムアウトなど結果不明の項目を自動再送しない。

## APIと責務境界

### 既存API

- `GET /favorite-prompts`：一覧と表示順を取得する。
- `GET /favorite-prompts/{favoritePrompt}`：差し替えに必要な完成プロンプトと選択スナップショットを取得する。
- `GET /lora-prompt-options`：現在と保存時の人物LoRA・トリガー情報を照合する。

お気に入り一覧・詳細APIが既に返す情報で差し替え準備できる場合は契約を増やさない。不足する識別情報だけがある場合は、プロンプト本文を一覧へ追加せず詳細APIへ最小限追加する。

### 一括送信API

既存`POST /comfyui/prompts/batch`を利用し、各項目の候補キーとしてお気に入り候補キーを許容する。サーバー側は候補キーを業務IDとして信用せず、結果対応用の不透明な文字列として扱う。人物LoRA ID、系統ID、positive、negativeは既存と同じ検証・業務ルールを適用する。

グループ保存用API、DBマイグレーション、Laravel側のグループモデルは追加しない。

## 失敗時の振る舞い

- お気に入り一覧取得失敗：現在のチェックやグループを削除せず、一括送信を開始しない。
- 詳細取得失敗：そのお気に入りを準備失敗として除外し、残りの準備を続ける。
- 差し替え不能：そのお気に入りを除外し、理由を表示する。
- 適用人物LoRAが未選択・非表示・削除済み・生成設定不正：一件も送信しない。
- 対応する系統のComfyUIワークフロー未設定または不正：一件も送信せず、共通エラーとして表示する。
- 一括送信通信自体が応答前に失敗：結果不明として扱い、自動再送しない。
- 項目単位の送信失敗：残りを続行し、成功・失敗・結果不明を集計する。
- グループ保存失敗：現在のチェックは画面内に維持し、保存済みグループを壊さない。

## 実装境界

- グループ構造の検証、同名判定、保存・呼び出し時の集合計算は、F21の考え方を再利用できる純粋なJavaScriptモジュールへ置く。意味が異なる候補キーや保存キーを無理に同一状態へ統合しない。
- お気に入り一覧のDOM、チェック状態、グループUI、詳細取得、差し替え準備、一括送信結果表示はお気に入りページ制御が調整する。
- 人物LoRAタグとトリガー範囲の特定・置換、および人物LoRA未保存時の挿入は、既存の人物LoRA差し替え用メタデータ処理とpositiveセクション合成処理を共通の純粋関数として利用・拡張する。元トリガーが見つからなくても置換を続ける既存経路は今回の一括処理には使わず、厳格な判定を追加する。DOMに文字列操作を埋め込まない。
- ComfyUI送信の認可、LoRA・系統・生成設定の整合性、ワークフロー適用は既存のApplication更新ユースケースとDomainの規則で保証する。

## 受入条件

1. 複数のお気に入りをチェックして名前を付けると、再読み込み後も同じブラウザーでグループを呼び出せる。
2. グループ呼び出し後にチェックを変更しても、明示的に上書きするまで保存済みグループは変わらない。
3. 削除済みお気に入りを含むグループを呼び出すと、利用可能な項目だけがチェックされ、不足件数が表示される。
4. 通常画面で選択中の人物LoRA、所属トリガー、強度が、人物LoRAを保存済みの対象では元人物LoRA・トリガーへ差し替えられる。
5. 人物LoRAを含めずに保存したお気に入りでは、現在選択中の人物LoRAとトリガーが既存のpositive構成順へ新規挿入される。
6. 各お気に入りのnegative、衣装LoRA、服装、その他のpositive文面は変更されない。
7. 保存済みの元人物LoRA部分を一意に特定できないお気に入りは送信されず、他の送信可能項目は処理される。
8. 人物LoRA未選択、送信可能項目0件、確認キャンセルではComfyUIへ送信されない。
9. 準備成功項目が100件を超える場合は送信されず、100件以下へ減らす案内が表示される。
10. 送信確認には対象人物LoRAと準備成功・除外件数が表示され、承認後だけ送信される。
11. 一件の送信失敗後も残りを処理し、お気に入り名ごとの成功・失敗・結果不明を確認できる。
12. 一括送信によってお気に入り本体と保存済みグループの内容は変更されない。
13. `localStorage`にはグループ名とお気に入り候補キーだけが保存され、プロンプト本文、画像、LoRA名を含まない。
14. `localStorage`が利用できない場合も、画面を閉じるまではチェック操作と一括送信を続けられる。

## 検証方針

- グループの検証・保存・呼び出し・削除・不足候補を、架空のお気に入りIDとFake Storageで単体テストする。
- 人物LoRAタグ・トリガーの正常な差し替え、未選択トリガー、人物LoRA未保存時の挿入、手編集による不一致、曖昧一致を純粋関数のテストで確認する。
- お気に入り一覧のチェック、グループUI、送信確認、処理中無効化、項目別結果をJSDOMとFake fetchで確認する。
- HTTPテストで一括送信の入力検証、人物LoRA・系統・生成設定の整合性、部分失敗と結果不明を確認する。
- ComfyUIはFakeを使い、実サービスへ送信しない。
- 実装時は`sh scripts/check.sh`、`docker compose run --rm -T app composer test`、フロントエンドビルドを実行する。ブラウザー確認は行わず、最終的な視認性と操作感を利用者確認事項として報告する。

## 設計者判断

- 初期チェックを全件未選択とした。お気に入り件数が増えたときの意図しない大量送信を避けるためである。
- 人物LoRAを保存していないお気に入りには、現在選択中の人物LoRAとトリガーを新規挿入する。利用者は保存済みお気に入りへLoRAを適用する用途を求めており、既存の構造化されたpositiveセクション合成規則で位置を決定できるためである。
- 詳細取得と差し替え可否の判定を送信確認前に行う。確認後に多数が除外され、利用者の期待と実送信件数がずれることを避けるためである。
- グループはお気に入りIDだけを保持する。お気に入りの改名や内容更新には追従し、削除時だけ不足として扱うためである。

## 未決事項

実装開始を妨げる未決事項はない。別端末同期、グループの並べ替え・改名は、利用状況を見て別機能として設計する。
