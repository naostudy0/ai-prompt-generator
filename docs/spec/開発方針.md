# 設計書ファースト・目的駆動開発の方針

## 1. この文書の位置づけ

このプロジェクトは、AIのプロンプト生成ツールをLaravelで開発する。
設計書を実装の出発点とし、DDD（ドメイン駆動設計）をベースに、利用者の目的から要件・振る舞い・実装を具体化する。

ここでいう「目的駆動開発」は本プロジェクトの開発方針であり、特定の標準手法の名称として扱わない。

PHP/Laravel、Blade、HTML、CSS、JavaScriptで、当面1ページ完結の画面を作る。
JavaScriptからAPIを呼び出して必要な情報の取得・更新を行う。CSSにはTailwindを利用してもよい。
業務処理の入口はHTTPとする。

対象利用者、生成方式、AIプロバイダー、保存・履歴・認証などの個別機能は未確定とする。
本書中の構成例は採用済みの機能仕様を意味しない。

## 2. 目的から実装へつなぐ

次の関係を設計書に残す。

| 段階 | 記述すること | 確認すること |
| --- | --- | --- |
| 目的 | 誰が、どの状況で、何を実現したいか。その理由 | UIや技術の導入そのものが目的になっていないか |
| 要件 | 目的を達成したと判断できる条件 | 観察・検証できる基準になっているか |
| 振る舞いの仕様 | 入力、事前条件、出力、状態変化、失敗時の振る舞い | 正常系だけでなく境界・異常系を説明できるか |
| 実装 | 仕様を実現するクラス、処理、DB、外部連携 | どの目的・要件のためのコードか説明できるか |

具体化するだけでなく、仕様や実装に疑問が生じたら目的に戻って見直す。
数値の上限や禁止条件などには、その制約が必要な業務上の理由を添える。
理由が不明な条件を、AIの推測で業務ルールとして確定しない。

## 3. 設計書の構成

文書は必要になった時点で作る。空の設計書を一括生成しない。

```text
docs/
├── spec/
│   ├── 開発方針.md                 # 本書：全作業で参照
│   ├── 機能概要.md                 # 利用者・目的・スコープ・機能一覧
│   └── 用語集.md                   # 業務用語と意味、適用する文脈
├── design/
│   ├── アーキテクチャ.md           # 責務・依存関係・境界の全体方針
│   └── features/
│       └── <機能ID>-<機能名>.md    # 要件・ユースケース・詳細設計・受入条件
├── review/
│   └── コードレビュー基準.md       # レビュー時の確認観点
└── decisions/
    └── <連番>-<判断名>.md          # 重要な設計判断と採用理由
```

### 機能概要

最初に作成し、次を記載する。

- 解決したい課題、対象利用者、利用場面、目指す状態。
- 対象範囲と対象外、優先順位、最初に動作させる最小範囲。
- 機能ID、機能名、目的、対応する詳細設計へのリンク。
- 確定事項、仮説、未決事項を区別した一覧。

### 用語集・全体設計

同じ言葉を設計書とコードで一貫して使う（ユビキタス言語）。
文脈によって意味やルールが異なる場合は、適用範囲を明示する。
境界づけられたコンテキストは業務上の意味と変更理由から検討し、画面やDBテーブルの単位で機械的に分割しない。

### 機能ごとの詳細設計

一つの文書に、次の順序で記述する。不要な項目には「対象外」と理由を書く。

1. 機能ID、設計状態（草案／実装可能／実装済み）、関連文書。
2. 利用者の目的と、その目的が必要な背景。
3. 要件とスコープ。要件には`F01-R01`のような識別子を付ける。
4. ユースケース。実行者、入力、事前条件、正常な流れ、出力・事後条件、例外の流れ。
5. 業務ルール。不変条件、境界値、状態遷移、各ルールの理由。
6. ドメイン設計。概念、責務、値オブジェクト、エンティティ、集約と整合性の範囲。必要なものだけ採用する。
7. 入出力設計。必要な画面・API・エラー表示、認可条件。
8. 永続化・外部連携。保存項目、制約、トランザクション境界、外部サービス失敗時の扱い。
9. 受入条件と検証方法。要件IDとの対応、正常系・境界値・異常系。
10. 未決事項、設計上の判断、関連する実装・テストの場所。

受入条件は「前提／操作／期待結果」で具体的に記述する。
AI連携が必要と確定した場合は、応答の揺らぎ、タイムアウト、費用、送信する情報の扱いを設計する。
生成結果の品質基準と、プログラムとして保証する振る舞いを区別する。

## 4. DDDと責務の分け方

### 同じ目的のデータとルールをまとめる

ドメインモデルは、業務ルールと正しい状態を守る役割を持つ。
値とその検証・操作をまとめ、不正な状態を生成・更新できないようにする。
値オブジェクトは原則として不変にし、操作で新しい値を作る際にも制約を適用する。

HTTPの入力検証だけに業務上の不変条件を任せない。複数のAPIから利用しても同じルールが守られるようにする。
ただし、入力形式の検証と業務ルールの検証は目的が違うため、すべてをドメインモデルに詰め込まない。

見た目の似た処理や同じ名称だけを理由に共通化しない。
目的・ルール・変更理由が同じかを確認し、違う場合は別の概念として扱う。
業務ルールの乏しい単純な処理に、不要な集約・サービス・インターフェースを増やさない。

### 各層の責務と依存関係

| 層 | 責務 | Laravelでの配置 |
| --- | --- | --- |
| プレゼンテーション | HTTPなどの入出力、形式検証、ユースケース呼び出し | `app/Http/` |
| アプリケーション | 利用者の目的を実行する手順、認可の調整、トランザクションの調整 | `app/Application/<文脈>/` |
| ドメイン | 業務ルール、不変条件、状態遷移 | `app/Domain/<文脈>/` |
| インフラ | DB、外部AIなどの具体的な入出力実装 | `app/Infrastructure/<文脈>/` |

具体的な配置・命名・依存関係・更新と参照の流れは[アーキテクチャ設計](../design/アーキテクチャ.md)に従う。
必要になるまでディレクトリや抽象クラスを先行作成しない。
ドメイン層はHTTP、Eloquent、外部SDKなどの具体的な実装に依存させない。
アプリケーション層はドメインと必要なインターフェースを利用し、インフラ層がそれを実装する。
DB・外部サービス境界のインターフェースは、それを必要とする側の層に置き、サービスプロバイダーで実装を結び付ける。

### 更新と参照、三つのモデル

- 更新系はドメインモデルを通して業務ルールと整合性を守り、必要な単位で保存する。
- 参照系はクエリサービスから表示用途のDTOを返す。更新用のドメインモデルの復元を必須にしない。
- 参照系でも認可やデータ公開範囲の制約は必ず守る。参照処理に業務上の更新を混ぜない。

ドメインモデル、参照用モデル、DBの永続化モデルは目的が異なる。
Eloquentモデルをそのままドメインモデルと見なさず、保存構造と業務概念を分けて設計する。

## 5. 開発の進め方

1. **文脈を読む**：本書、機能概要、用語集、該当する設計・設計判断を読む。
2. **目的を整理する**：利用者・課題・成功条件・対象外を機能概要に記載する。重要な未決事項はユーザーに確認する。
3. **小さな機能を選ぶ**：一つの利用目的を実現できる範囲に区切り、関連する用語と境界を整理する。
4. **詳細設計を先に書く**：要件から受入条件までを結び付け、正常系・境界・失敗時の扱いを具体化する。
5. **実装可能か判断する**：目的、業務ルール、受入条件が明確で、実装を左右する未決事項が解消していることを確認する。
6. **実装する**：設計に沿って小さな単位で実装する。業務ルールの単体テスト、ユースケースやDB・HTTP境界のテストを必要に応じて作る。
7. **目的に照らして検証する**：[コーディング規約](../design/コーディング規約.md)に従って必須の静的チェックを実行する。受入条件とテスト結果を対応付け、必要な動作確認を行う。
8. **文書と結果を揃える**：関連する実装・テストの場所、検証結果、残った制限を記録し、設計状態を更新する。

「設計のみ」という依頼では文書作成までとする。
実装まで依頼されている場合、明確な範囲の通常の技術判断は理由を記録して進め、各工程で一律に承認待ちにしない。
利用目的、業務ルール、範囲、費用・データの扱いを左右する未決事項は推測で確定せず、確認が取れるまで該当部分の実装を保留する。

## 6. 変更時とAIによる作業のルール

- 振る舞いの追加・変更は、対応する設計書を先に更新してから実装する。設計と実装は同じ変更単位で揃える。
- 実装中に設計上の問題が見つかったら、コードだけで仕様を変えず、目的・要件へ戻って設計を修正する。
- 不具合修正は、期待する振る舞いが既存設計にあるか確認する。欠けていれば追記し、必要な回帰テストを用意する。
- 振る舞いを変えないリファクタリングでは、影響する構造・設計判断を更新する。無関係な文書の更新は不要。
- 大きな境界変更や技術選定は、判断記録に背景、選択肢、採用理由、影響を残す。
- AIは着手時に参照した設計書と作業範囲を示し、完了時に変更点、検証結果、未解決事項を報告する。
- 設計にない機能や抽象化を、将来役立ちそうという理由だけで追加しない。
- 文書のみの変更ではリンクや内容の整合性を確認する。アプリの依存追加やテスト実行を必須にしない。

## 7. 完了の基準

- 目的、要件、仕様、実装、検証の対応が追える。
- 業務ルールが適切な責務にまとまり、不正な状態や許可されない操作を防げる。
- 更新・参照・保存の目的が混ざっていない。
- 受入条件を満たした証拠があり、未実行の検証や制限を明記している。
- 設計書と実装が一致し、未確定事項が実装済みの仕様として紛れ込んでいない。

次の工程では、まず`docs/spec/機能概要.md`を作り、対象利用者・解決したい課題・最初の機能範囲を具体化する。
