# 0003 フロントエンド構成の継続

## 状況

入力セクション、選択状態、登録用モーダルが増え、左右の補助メニューから複数機能の状態を参照する必要が生じた。React、Vue、Next.jsなどへ移行して状態管理と部品化を行う選択肢がある。

現在はLaravel Bladeが画面の骨組みを返し、機能ごとのJavaScriptモジュールがAPI通信、選択状態、部分描画を担当している。ページ遷移、サーバー描画とクライアント描画の併用、外部公開用SEO、複数画面で共有する複雑なUI部品は必要になっていない。

## 判断

F10では現在のBladeとJavaScriptモジュール構成を継続する。各機能コントローラーから表示用のナビゲーション項目と選択概要を通知し、ページコントローラーが左右メニューを描画する。

選択状態の正本は各機能コントローラーに残し、共通ストアを新設しない。左右メニューは受け取った状態を表示する投影として扱う。

## 理由

- 今回必要なのは既存状態の集約表示であり、ルーティングやサーバー描画を含むアプリ全体の置き換えを必要としない。
- ReactまたはVueへの部分移行ではBladeとの境界と状態同期が増え、全面移行では動作済みの登録・選択・モーダル・テストを広範囲に作り直すことになる。
- 通知するスナップショットの契約を明確にすれば、機能モジュール間を直接参照せずに追加セクションへ追従できる。
- Next.jsは別のサーバー実行環境とルーティングを持ち込むため、Laravelで完結する現在の構成には過剰である。

## 影響

- F10はBlade、CSS、JavaScriptの変更として実装し、新しいフロントエンド依存を追加しない。
- 各画面コントローラーは状態変化を通知する共通形式へ合わせる。
- メニュー描画と状態スナップショットのテストを追加し、中央領域の入力・フォーカス・スクロール位置に影響しないことを確認する。

## 見直し条件

複数画面で同じ対話部品と状態を共有する、画面間ルーティングをクライアント側で管理する、または状態通知の接続が増えて変更時の追跡が困難になった場合は、ReactまたはVueを含むコンポーネント基盤と状態管理を改めて比較する。
