# 0001: 初期アーキテクチャ

- 状態：採用（今後の実装に適用。コードへの一括適用は未実施）
- 日付：2026-09-16
- 対象：[アーキテクチャ設計](../design/アーキテクチャ.md)

## 背景

設計書を起点に、目的駆動開発とDDDでAIプロンプト生成ツールを作る。
更新は正しい状態を作ること、参照は必要な情報を返すことを目的とする。
機能と業務の境界は未確定であり、初期段階から運用上の構成を複雑にする根拠はない。

## 判断

1. 単一のLaravelアプリケーション内で文脈を分ける。サービス分割は行わない。
2. 層を上位、文脈を下位に置く。既存の開発方針とLaravel標準配置を維持し、役割と依存方向を確認しやすくする。
3. ApplicationとHTTP入口で更新・参照を分ける。Domainは更新の業務ルール、参照DTOはApplication、保存モデルはInfrastructureに置く。
4. 更新・参照は当初同じDBを利用する。参照用DB、イベントソーシング、メッセージバスは導入しない。
5. DomainとApplicationはLaravelや外部SDKから独立させ、必要な境界をインターフェースで表現する。
6. 一つのHandlerを一つの利用目的に対応させる。汎用の処理振り分け基盤や基底Repositoryは導入しない。
7. PHP/Laravel、Blade、HTML、CSS、JavaScriptで1ページ構成とし、必要な取得・更新を同一アプリのAPIで行う。Tailwindは利用可とする。
8. 更新の配置名は`Writes`、参照は`Queries`とする。業務用CLI／Artisanコマンドは現時点では作らず、HTTPを入口とする。

## 比較した選択肢

| 選択肢 | 判断理由 |
| --- | --- |
| 文脈を最上位に置く構成 | 文脈単位の変更をまとめやすいが、今回は既存方針との整合性と層の見通しを優先する |
| Controller・Eloquent中心の構成 | 初期実装は簡単だが、今回重視する業務ルールと保存・入出力の分離を明示しにくい |
| 更新・参照のDB分離 | 独立した最適化が可能だが、同期・遅延・復旧の設計が増える。現時点で必要性がない |
| マイクロサービス | 独立デプロイが可能だが、通信や分散整合性の負担がある。文脈を学ぶ段階では採用しない |

## 結果と負担

参照と更新をそれぞれの目的に合わせて変更・検証できる。
一方、DTO・インターフェース・変換処理が増えるため、必要な境界に限定し、単純な処理に不要な抽象化を足さない。
同一文脈のコードは複数の層に分かれるため、命名を揃え、詳細設計から実装への対応を記録する。

## 見直す条件

独立した開発・デプロイが必要になった場合、文脈単位での配置やサービス分割を検討する。
参照負荷や応答時間の計測で同一DBの限界が確認された場合、参照の最適化やDB分離を検討する。
変更時は計測結果または具体的な業務上の理由を残し、移行と運用の負担も比較する。
