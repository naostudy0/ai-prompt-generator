# 0005 外部LLM連携の境界

## 状態

採用。機能固有の入出力、失敗、UI、受入条件は[F20 AIプロンプト生成](../design/features/F20-AIプロンプト生成.md)で管理する。

## 背景

日本語のイラスト説明から画像生成用の英語プロンプト候補を作りたい。生成には外部LLMのHTTP APIを使うが、ユースケースに接続先、通信ライブラリ、プロバイダー固有のJSONを漏らすと、テストと接続先の変更が難しくなる。

一方、初回はOllama Chat API互換の応答だけを対象とする。将来利用するか不明な複数プロバイダーを先回りして実装する必要はない。

## 判断

- Applicationに「イラスト説明から一組の画像生成用プロンプトを生成する」ポートを置く。
- InfrastructureにOllama Chat API互換アダプターを一つ実装する。SDKは前提とせず、Laravel HTTPクライアントを使う。
- ApplicationとHTTP入出力にはOllama固有のリクエスト・レスポンス型を漏らさない。
- 接続先、モデル、接続タイムアウト、応答タイムアウトはサーバー側の設定と環境変数から与える。利用者入力から任意URLを受け取らない。
- System Promptはスタイル別の専用資材とし、PHPクラスの長文リテラルにしない。
- 外部通信はDBトランザクション外で同期実行する。初回はDB保存もQueue処理も行わない。
- アダプターは上流の構造化応答と性能指標をアプリケーション向けの結果へ変換し、不正応答と通信失敗を意味のある失敗に分ける。

## 理由

外部LLMの配置場所と実行環境を機能仕様から切り離し、設定されたAPIを同じユースケースで利用できる。ポートのFakeでApplicationを、HTTP Fakeでアダプターを検証できる。初回の具体実装を一つに限ることで、差し替え可能性を保ちつつ過剰設計を避ける。

## 影響

- 運用時はLaravel実行環境から設定先APIへ到達できる必要がある。
- 接続先固有の認証が必要になった場合は、秘密情報をサーバー側設定で管理し、アダプター内で適用する。
- 外部LLMを切り替える場合も、新しいアダプターがApplicationポートの意味と応答検証を守る。
- 同期応答が実用上待てない時間になった場合は、Queue化と結果取得方法を別の設計で決める。

## 比較した選択肢

### ControllerからLLM APIを直接呼ぶ

少ないファイルで始められるが、HTTP入出力、利用者の目的、プロバイダー固有通信が混在し、既存の層の分離に反するため採用しない。

### 初回から複数LLMプロバイダーを実装する

切り替えをすぐ検証できるが、現在の目的に必要ない設定、認証、応答差分まで実装することになるため採用しない。
